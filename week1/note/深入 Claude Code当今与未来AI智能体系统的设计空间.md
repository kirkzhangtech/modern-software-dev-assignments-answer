## 摘要

Claude Code 是一款智能体式(agentic)编程工具,可以代表用户运行 shell 命令、编辑文件并调用外部服务。本研究通过分析其公开可得的 TypeScript 源码(v2.1.88)来描述其完整架构,并进一步将其与两个独立的开源 AI 智能体系统 OpenClaw 和 Hermes Agent 进行对比;这两个系统在不同的部署场景下回答了许多相似甚至相同的设计问题。我们的分析识别出驱动该架构的五项人类价值、理念与需求:人类决策权、安全与隐私、可靠执行、能力放大,以及情境适应性。随后,我们通过十三条设计原则,将它们追溯到具体的实现选择。系统的核心是一个简单的 while 循环:调用模型、运行工具、重复。然而,大部分代码都位于这个循环周围的系统之中:具有七种模式和一个基于机器学习的分类器的权限系统、用于上下文管理的五层压缩(compaction)流水线、四种扩展机制(MCP、插件、skills 与 hooks)、子智能体委派与编排机制,以及面向追加(append-oriented)的会话存储。

与 OpenClaw(多渠道个人助理网关)和 Hermes Agent(单进程、多界面助理)的比较表明,同样的设计问题在三种部署场景下会产生不同的答案。Claude Code 强调逐操作(per-action)的安全,OpenClaw 强调边界级(perimeter-level)的访问控制,而 Hermes 则在众多界面上呈现逐操作的审批。在运行时层面,Claude Code 使用单一的 CLI 循环,OpenClaw 将运行时嵌入网关控制平面,Hermes 使用单一进程,其角色由入口点决定。在上下文与扩展层面,Claude Code 扩展上下文窗口,OpenClaw 注册全网关范围的能力,Hermes 则提供可插拔的记忆与模型后端。最后,我们基于近期的实证、架构与政策文献,为未来的智能体系统指出六个开放的设计方向。我们的 GitHub 地址:https://github.com/VILA-Lab/Dive-into-Claude-Code。

## 1 引言

AI 辅助软件开发已经从 GitHub Copilot(Chen et al., 2021)这类自动补全式工具,发展到 Cursor(Cursor, 2026)这样集成于 IDE 的助手,再到能够自主规划多步修改、执行 shell 命令、读写文件并对自身输出进行迭代的完全智能体式系统。Claude Code(Anthropic, 2026a)是 Anthropic(Anthropic, 2026e)发布的一款智能体式编程工具。其官方文档描述了一个"智能体循环(agentic loop)":规划并执行动作以达成目标,可以调用工具、评估结果,并持续进行直到任务完成¹。这种从"建议"到"自主行动"的转变,带来了基于补全的工具所不具备的架构要求。这些要求界定了一个设计空间,即一组反复出现的问题,涉及安全、上下文管理、可扩展性和委派等主题,每个编程智能体都必须应对。本研究通过对 Claude Code 的源码级分析,展示一个生产级系统如何回答这些问题。

> ¹ https://code.claude.com/docs/en/how-claude-code-works

尽管采用率不断增长,Anthropic 只发布了面向用户的 Claude Code 文档,而没有发布详细的架构描述。本研究利用源码分析来描述其架构设计决策。Anthropic 对 132 名工程师和研究人员的内部调查(Huang et al., 2025)显示,约 27% 的 Claude Code 辅助任务属于"没有这个工具就不会去尝试"的工作,这表明该架构带来的是质的新工作流,而不仅仅是对现有工作流的加速。

在本工作中,我们首先识别出驱动该架构的五项人类价值/理念和十三条设计原则(第 2 节),然后将分析组织为三个部分:

1. **设计空间分析。** 我们识别出反复出现的设计问题(推理位于何处、迭代循环如何构造、采取何种安全姿态、扩展面如何划分、上下文如何管理、工作如何在子智能体之间委派,以及会话如何持久化),并通过一个由 7 个组件构成的高层结构和一个 5 层的子系统架构来分析 Claude Code 的回答,将每个选择追溯到具体的源文件(第 3 节)。该分析旨在深入理解系统机制,以期为设计更好、更强大的智能体系统提供参考。

2. **与 OpenClaw 和 Hermes Agent 的架构对比。** 除了分析 Claude Code 本身,我们还在六个设计维度上,将其设计理念与两个开源智能体系统进行比较:OpenClaw(Steinberger and OpenClaw Contributors, 2026,多渠道个人助理网关)和 Hermes Agent(Nous Research, 2026,单进程、多界面助理)。目的是展示同样的反复出现的问题在不同部署场景下如何产生不同的答案(第 10 节),从而凸显商业软件与开源软件之间的共同原则与关键差异。这一比较有助于揭示部署环境、产品目标、安全要求和用户假设如何以不同方式塑造架构选择。通过考察这些系统在何处趋同、何处分歧,本研究希望为未来更强大的智能体系统的设计提供有益的指导与实践洞见。

3. **未来智能体系统的开放方向。** 在设计空间分析以及与 OpenClaw、Hermes 的对比基础上,第 13 节指出六个开放方向:可观测性—评估鸿沟、跨会话持久化、harness 边界的演进、时间跨度扩展(horizon scaling)、治理,以及开发者长期能力;每个方向都参考了实证、架构和政策文献。长期能力问题还揭示了一个开放的担忧:Claude Code 智能体系统放大了程序员和终端用户的短期能力,但对于明确支持人类长期提升、更深入理解和持续的代码库一致性,它提供的机制有限。

核心智能体循环是一个带状态管理的 while-true 循环。围绕它的安全、扩展性、上下文管理、委派和持久化等子系统,构成了实现的主体。源码级分析²使我们能够直接从系统本身识别设计选择、子系统边界和实现权衡,而不是仅仅依靠产品描述来推断。

**论文结构。** 第 2 节识别驱动该架构的人类价值和设计原则。第 3 节介绍高层架构及其回答的设计问题。第 4 至 9 节各自分析一个主要子系统的设计选择。第 10 节将分析与 OpenClaw 和 Hermes Agent 进行对比,第 11 节将本工作置于先前的智能体和软件工程文献之中,第 12 节进行讨论,第 13 节梳理未来智能体系统的开放问题,第 14 节总结。附录描述了证据基础与方法论、包结构说明、社区重新实现,以及一份从新的智能体系统信号到本文设计空间问题的配套映射。

## 2 设计理念、设计原则与架构动机

生产级编程智能体由人类构建、为人类服务,它们所嵌入的架构决策反映了其创造者认为什么是重要的。本节识别驱动 Claude Code 设计的人类价值,通过反复出现的设计原则追溯这些价值,并给出组织第 3 至 9 节分析的设计空间问题。

Anthropic 的安全智能体框架陈述了一个核心张力:"智能体必须能够自主工作;它们的独立运行恰恰是其价值所在。但人类应当保留对其如何追求目标的控制权"(Anthropic, 2025a)。Claude 的《宪章》(Constitution)并非通过僵化的决策流程来解决这一点,而是通过培养"能够在情境中灵活运用的良好判断力和健全价值观"(Anthropic, 2026b)。这些承诺,加上关于开发者实际如何使用该工具的实证发现(Huang et al., 2025;McCain et al., 2026),指向塑造该架构的五项人类价值。

### 2.1 五项价值与理念

**人类决策权(Human Decision Authority)。** 人类对系统所做的事情保留最终决策权,通过一个主体层级(principal hierarchy,依次为 Anthropic、运营方、用户)来组织,它规范了谁对什么拥有权限(Anthropic, 2026b)。系统的设计使人类能够行使知情控制:他们可以实时观察动作、批准或拒绝拟议的操作、中断可中断的进行中操作,并在事后审计。当 Anthropic 发现用户会批准 93% 的权限提示时(Hughes, 2026),其应对并非增加更多警告,而是重构问题:设定明确的边界(沙箱、自动模式分类器),让智能体在边界内自由工作,而不是采用用户习以为常后便不再审阅的逐操作审批(Dworken and Weller-Davies, 2025)。

**安全、保障与隐私(Safety, Security, and Privacy)。** 系统保护人类、其代码、数据和基础设施免受伤害,即使人类疏忽或犯错。这与"人类决策权"不同:决策权关乎人类做出选择的权力,而安全关乎系统即使在这种权力失效时也有义务进行保护。Anthropic 的安全智能体框架另外将保障智能体交互的安全,以及在长时间交互中保护隐私,确定为核心承诺(Anthropic, 2025a)。自动模式威胁模型(Hughes, 2026)明确针对四类风险:过度积极的行为、诚实的错误、提示注入(prompt injection)和模型失准(misalignment)。

**可靠执行(Reliable Execution)。** 智能体做人类真正想要的事,长期保持连贯,并支持在宣布成功之前验证其工作。这一价值既涵盖单轮正确性(它是否忠实地理解了请求?),也涵盖长时程的可靠性(它在跨越上下文窗口边界、会话恢复和多智能体委派时是否仍保持连贯?)。Anthropic 的产品文档(Anthropic, 2026f)描述了智能体重复直到任务完成的三阶段循环:收集上下文、采取行动、验证结果。智能体设计指南(Schluntz and Zhang, 2024)进一步强调,每一步来自环境的"真实依据(ground truth)"用以评估进展。harness 设计指南(Rajasekaran, 2026)同样指出,"智能体往往会自信地称赞自己的工作",即使质量平平,这促使将生成与评估分离。

**能力放大(Capability Amplification)。** 系统在单位努力和成本下,实质性地提升人类所能完成的事。第 1 节讨论过的 Anthropic 内部调查(Huang et al., 2025)表明,该架构带来的是质的新工作流,而不仅仅是更快的既有工作流:约 27% 的任务属于本来不会去尝试的工作。其创造者将该系统描述为"一个 Unix 工具,而非传统意义上的产品",由"有用、可理解且可扩展"的最小构建块组成(Cherny and Wu, 2025)。该架构投入于确定性的基础设施(上下文管理、工具路由、恢复),而不是决策脚手架(显式的规划器或状态图),其前提是:越来越强大的模型,从丰富的运行环境中获益,多于从约束其选择的框架中获益。

**情境适应性(Contextual Adaptability)。** 系统适应用户的具体情境(其项目、工具、约定和技能水平),并且这种关系随时间不断改善。扩展架构(CLAUDE.md、skills、MCP、hooks、插件)在多个上下文成本层级上提供可配置性(第 6 和第 7 节)。纵向数据(McCain et al., 2026)表明,人—智能体关系是演化的:自动批准率从不足 50 个会话时的约 20%,上升到 750 个会话时的 40% 以上。这一模式被描述为"由模型、用户和产品共同构建"的自主性,意味着系统是为信任的轨迹而设计的,而不是固定的信任状态。MCP 捐赠给 Linux 基金会的 Agentic AI Foundation(The Linux Foundation, 2025),体现了这一价值的生态维度。

### 2.2 设计原则

这些价值通过十三条设计原则得以落实,每条原则回答一个生产级编程智能体必须解决的反复出现的问题。表 1 总结了这些原则;后续各节(第 3 至第 9 节)通过具体的实现选择追溯每一条原则。

**表 1** 设计原则、它们所服务的价值,以及每条原则所回答的设计空间问题。一条原则可对应多项价值;实现见所列章节。

| 原则 | 所服务的价值 | 设计问题 | 章节 |
|---|---|---|---|
| 默认拒绝并升级给人类(Deny-first with human escalation) | 决策权、安全 | 对未识别的动作应当允许、阻止,还是升级给人类? | 5, 8, 9 |
| 渐进式信任谱系(Graduated trust spectrum) | 决策权、适应性 | 固定的权限级别,还是用户随时间逐步推进的谱系? | 5 |
| 分层机制的纵深防御(Defense in depth with layered mechanisms) | 安全、决策权、可靠性 | 单一安全边界,还是采用不同技术的多重叠加边界? | 3, 5 |
| 外部化的可编程策略(Externalized programmable policy) | 安全、决策权、适应性 | 硬编码策略,还是带生命周期 hooks 的外部化配置? | 5, 6 |
| 将上下文视为稀缺资源并渐进管理(Context as scarce resource with progressive management) | 可靠性、能力 | 约束性资源是什么、如何管理:单次截断,还是分级流水线? | 4, 6, 7, 8 |
| 仅追加的持久状态(Append-only durable state) | 可靠性、决策权 | 可变状态、检查点快照,还是仅追加日志? | 4, 9 |
| 最小脚手架、最大运行 harness(Minimal scaffolding, maximal operational harness) | 能力、可靠性 | 投入于脚手架侧的推理,还是投入于让模型自由推理的运行基础设施? | 3, 4 |
| 价值观优先于规则(Values over rules) | 能力、决策权 | 僵化的决策流程,还是以确定性护栏为后盾的情境判断? | 3, 5, 7 |
| 可组合的多机制扩展性(Composable multi-mechanism extensibility) | 能力、适应性 | 一个统一的扩展 API,还是按不同上下文成本分层的机制? | 6 |
| 按可逆性加权的风险评估(Reversibility-weighted risk assessment) | 能力、安全 | 对所有动作采用相同的监督,还是对可逆和只读动作采用较轻的监督? | 4, 5, 8 |
| 透明的基于文件的配置与记忆(Transparent file-based configuration and memory) | 适应性、决策权 | 不透明的数据库、基于嵌入的检索,还是用户可见、可版本控制的文件? | 7 |
| 隔离的子智能体边界(Isolated subagent boundaries) | 可靠性、安全、能力 | 子智能体共享父级的上下文和权限,还是隔离运行? | 8 |
| 优雅恢复与韧性(Graceful recovery and resilience) | 可靠性、能力 | 遇到错误就硬失败,还是静默恢复并把人类的注意力留给无法恢复的情况? | 4, 5 |

这些原则可以与三大类备选设计家族对照来理解。第一类是基于规则的编排:LangGraph(LangChain, Inc., 2024)等框架把决策逻辑编码为带类型边的显式状态图,选择了脚手架而非最小 harness。第二类是容器隔离执行:SWE-Agent 和 OpenHands(Yang et al., 2024;Wang et al., 2024b)依赖 Docker 隔离,而非分层的策略执行。第三类是以版本控制作为安全保障:Aider(Gauthier, 2024)等工具把 Git 回滚作为主要安全机制,而不是默认拒绝式的评估。Claude Code 的原则集合的独特之处在于:将最小的决策脚手架与分层的策略执行相结合,将基于价值观的判断与默认拒绝相结合,并将渐进式的上下文管理与可组合的扩展性相结合。

**图 1** Claude Code 的高层系统结构。系统分解为七个功能组件:用户、界面、智能体循环、权限系统、工具、状态与持久化,以及执行环境。所有入口界面都汇聚到同一个智能体循环。

### 2.3 从价值到架构

每项价值都经由其原则追溯到具体的架构决策:

- **人类决策权**推动了:默认拒绝式评估、渐进式信任谱系、仅追加状态(可审计的历史)、外部化的可编程策略,以及价值观优先于规则(第 5 至 7 节和第 9 节)。
- **安全、保障与隐私**推动了:纵深防御、默认拒绝、按可逆性加权的评估、外部化策略,以及隔离的子智能体边界(第 5 和第 8 节)。
- **可靠执行**推动了:将上下文视为稀缺资源、仅追加的持久状态、优雅恢复、隔离的子智能体边界,以及纵深防御(第 4 节和第 7 至 9 节)。
- **能力放大**推动了:最小脚手架、可组合的扩展性、按可逆性加权的风险、上下文管理,以及优雅恢复(第 4 至 6 节)。
- **情境适应性**推动了:透明的基于文件的记忆、可组合的扩展性、渐进式信任谱系,以及外部化的可编程策略(第 5 至 7 节)。

这些映射也揭示了该架构"不做什么":它不会对模型的推理强加显式的规划图,不提供单一统一的扩展机制,也不会在恢复(resume)时还原所有会话范围内与信任相关的状态。这些"缺席"与上述原则集合是一致的。

### 2.4 一个贯穿性问题:开发者的长期能力

上述五项价值描述了该架构旨在服务什么。本文还提出第六个问题:该架构是否有助于开发者保持长期的理解力和能力。这一担忧是真实存在的:Anthropic 自己对 132 名工程师和研究人员的研究(Huang et al., 2025)记录了一种"监督悖论":对 AI 的过度依赖有可能使监督它所需的技能萎缩;独立研究(Shen and Tamkin, 2026)发现,在 AI 辅助条件下的开发者,理解力测试得分低 17%。然而,这一担忧在架构中,或在 Anthropic 所陈述的设计价值中,并未被突出地体现为一个设计驱动因素。因此我们不把它当作一项同等地位的价值,而是视为一个贯穿性的关注点:在第 12 节中,它是一个应用于全部五项价值的问题,即短期的能力放大是否以长期的人类理解、代码库一致性和开发者人才梯队为代价。

## 3 架构概览

构建一个生产级编程智能体,需要回答几个反复出现的设计问题:推理应当位于何处、需要多少个执行引擎、采取何种安全姿态,以及将什么资源视为约束性资源。Claude Code 的架构可以被解读为对这些问题的一组回答。在实现层面,系统由七个组件通过一条主数据流连接而成:用户通过若干界面之一提交提示词,提示词被送入共享的智能体循环。智能体循环组装上下文、调用 Claude 模型、接收可能包含工具调用请求的响应,将这些请求交由权限系统处理,并把获批的动作分派给与执行环境交互的具体工具。在整个过程中,状态与持久化机制记录对话转录、管理会话标识,并支持恢复(resume)、分叉(fork)和回退(rewind)操作。

### 3.1 设计问题与运行示例

描述围绕四个在生产级编程智能体中反复出现的设计问题展开,每个问题都对应表 1 中确定的一条或多条设计原则。每个问题在此处先给出 Claude Code 的答案,并说明可能的替代方案,然后在第 4 至 9 节中逐步展开演示。

**推理位于何处?** 在 Claude Code 中,由模型推理该做什么;由 harness 负责执行动作。模型在其响应中发出 tool_use 块,harness 解析它们、检查权限、分派给工具实现并收集结果(query.ts)。模型从不直接访问文件系统、运行 shell 命令或发起网络请求。这种分离带来了安全上的后果:由于推理与强制执行位于不同的代码路径,一个被攻破或被对抗性操纵的模型,无法绕过 harness 中实现的沙箱、权限检查或默认拒绝规则。模型与外部世界之间唯一的接口是结构化的 tool_use 协议,harness 在执行前会对其进行验证。对提取出的源码的社区分析估计,Claude Code 代码库中只有约 1.6% 属于 AI 决策逻辑,其余 98.4% 是运行基础设施,这一比例说明了核心智能体推理层有多薄。其他设计则更多地投入于脚手架侧的推理:Devin 维护显式的规划和任务跟踪结构,而 LangGraph(LangChain, Inc., 2024)则通过开发者定义的状态图来路由控制流。

**需要多少个执行引擎?** 无论用户是通过交互式终端、无头(headless)CLI 调用、Agent SDK 还是 IDE 集成与之交互,Claude Code 都使用同一个 queryLoop() 函数来执行(query.ts)。只有渲染和用户交互层有所不同。其他系统使用特定模式的引擎:例如,IDE 集成可能走与 CLI 工具不同的代码路径,以统一性换取针对特定界面的优化。

**默认的安全姿态是什么?** Claude Code 的默认安全姿态是"默认拒绝并升级给人类":拒绝规则优先于询问规则,询问规则优先于允许规则,未识别的动作会被升级给用户,而不是被静默放行(permissions.ts)。多个独立的安全层(权限规则、PreToolUse hooks、启用时的自动模式分类器,以及可选的 shell 沙箱)并行生效,因此任何一层都可以阻止一个动作(第 5 节)。这结合了表 1 中的"默认拒绝并升级给人类"与"分层机制的纵深防御"两条原则。其他方案则将信任边界放在别处:SWE-Agent 和 OpenHands(Yang et al., 2024;Wang et al., 2024b)依赖基于容器的隔离来约束任意执行,而 Aider(Gauthier, 2024)则以基于 git 的回滚作为主要的安全网。

**约束性资源是什么?** 在 Claude Code 中,上下文窗口(较旧的模型为 200K,Claude 4.6 系列为 1M)是约束性资源。每次模型调用之前都会执行五种不同的上下文缩减策略(query.ts),并且其他若干子系统决策(指令的懒加载、延迟加载的工具模式、仅返回摘要的子智能体)也是为了限制上下文消耗而存在(第 7 节)。之所以采用五层流水线,是因为没有任何单一的压缩策略能够应对所有类型的上下文压力。预算缩减(budget reduction)针对超出大小限制的单个工具输出;裁剪(snip)处理时间深度;微压缩(microcompact)应对缓存开销;上下文折叠(context collapse)管理超长历史;自动压缩(auto-compact)作为最后手段执行语义压缩。每一层在成本与收益之间采取不同的权衡,较早、较廉价的层先于较昂贵的层运行。其他架构则把别的资源视为主要瓶颈,例如计算预算(限制模型调用或工具调用的次数),或工作记忆(维护一个显式的草稿本,而不是依赖对话历史)。

**图 2** 运行时的回合流程,展示单个智能体回合的端到端执行:用户提示词经由上下文组装进入,调用模型,工具请求通过权限闸门,工具结果回馈到循环中,压缩机制管理上下文压力。

*(图示:用户提示词 → 上下文组装(设置、历史)→ 第 1 次迭代:工具请求 → 权限判定 → 允许则执行(同步 | 子智能体 | 后台)→ 结果;上下文压力大时进行压缩;第 2 次迭代:工具请求 → 权限判定 → 拒绝则返回"拒绝反馈";……;第 N 次迭代:无工具调用 → 助手响应 → 用户阅读并回复。)*

**运行示例。** 为了让这些原则落地,我们让同一个任务贯穿第 3 至 9 节:"修复 auth.test.ts 中失败的测试。"在本节中,用户通过 Claude Code 的某个界面提交提示词。后续各节追踪该请求经过查询循环、权限闸门、工具池、上下文窗口、子智能体委派和会话持久化的全过程。

### 3.2 高层系统结构

七组件模型(图 1)与源文件直接对应:

1. **用户(User):** 提交提示词、批准权限、审阅输出。
2. **界面(Interfaces):** 交互式 CLI、无头 CLI(claude -p)、Agent SDK,以及 IDE/桌面端/浏览器。所有界面都汇入同一个循环。
3. **智能体循环(Agent loop):** 由模型调用、工具分派和结果收集组成的迭代周期,在 query.ts 中实现为 queryLoop() 异步生成器。
4. **权限系统(Permission system):** 默认拒绝的规则评估(permissions.ts)、自动模式的 ML 分类器,以及基于 hook 的拦截(types/hooks.ts)。
5. **工具(Tools):** 多达 54 个内置工具(19 个无条件提供,35 个取决于功能开关和用户类型),通过 assembleToolPool()(tools.ts)组装,并与 MCP 提供的工具合并。插件通过 MCP 服务器以及 skill/命令注册表间接贡献工具。
6. **状态与持久化(State & persistence):** 以仅追加为主的 JSONL 会话转录(sessionStorage.ts)、全局提示词历史(history.ts),以及子智能体的侧链(sidechain)文件。
7. **执行环境(Execution environment):** 带可选沙箱的 shell 执行(shouldUseSandbox.ts)、文件系统操作、网页抓取、MCP 服务器连接以及远程执行。

数据流沿着一条从左到右的主轴:用户通过界面提交请求,进入智能体循环。循环向权限系统提出动作;获批的动作到达工具,工具与执行环境交互,并把 tool_result 消息返回给循环。状态与持久化与循环并行存在,负责记录转录并加载先前的会话数据。

应用入口 main()(位于 main.tsx)会初始化安全设置(包括 NoDefaultCurrentDirectoryInExePath,用以防止 Windows PATH 劫持)、注册用于优雅关闭的信号处理程序,并分派到相应的执行模式。

### 3.3 分层的子系统分解

五层分解(图 3)将七组件模型扩展为更细粒度的视图,把每一层映射到具体的源码目录。

**图 3** 展开的分层架构,展示五个子系统层:界面层(交互式 CLI、无头 CLI、Agent SDK、IDE/桌面端/浏览器、UI/渲染器)、核心层(智能体循环、压缩流水线)、安全/动作层(含自动模式分类器的权限系统、hook 流水线、扩展性、内置工具、MCP 工具、shell 沙箱、子智能体派生)、状态层(上下文组装、运行时状态、会话持久化、CLAUDE.md + 记忆、侧链转录),以及后端层(执行后端、外部资源)。

**界面层(入口点与渲染)。** src/entrypoints/ 目录包含启动路径,包括带有 coreTypes.ts、controlSchemas.ts 和 coreSchemas.ts 的 SDK 入口。src/screens/ 目录组合全屏布局,src/components/ 通过 ink 框架提供终端 UI 构建块。交互式 CLI 启动带有实时流式输出、权限对话框和进度指示器的终端 UI。无头 CLI(claude -p)创建一个 QueryEngine 实例(围绕共享查询路径的一个轻量对话封装,见 3.4 节),用于单次处理。Agent SDK 则通过异步生成器发出带类型的事件。

**核心层(智能体循环、压缩流水线)。** queryLoop() 异步生成器(query.ts)实现迭代式智能体循环,从状态层获取已组装的上下文,并把工具请求分派给安全/动作层。在每次模型调用之前,一条由五个顺序执行的整形器(shaper)组成的压缩流水线(query.ts:365-453)管理上下文压力:预算缩减、裁剪、微压缩、上下文折叠和自动压缩(第 4.3 节和 7.3 节)。

**安全/动作层(权限系统、hooks、扩展性、工具、沙箱、子智能体)。** 权限系统(permissions.ts)实现默认拒绝的规则评估,最多有七种权限模式(如果把仅内部使用的 bubble 和受功能开关控制的 auto 也算在内,types/permissions.ts),并集成了自动模式的 ML 分类器(yoloClassifier.ts),该分类器提供"快速过滤 + 思维链评估"两阶段的工具安全性判定(第 5 节)。一条涵盖 27 种事件类型的 hook 流水线(coreTypes.ts;输出模式见 types/hooks.ts)可以阻止、改写或标注工具请求;其中 5 种与安全相关,其余 22 种服务于生命周期和编排目的(第 6 节)。扩展性子系统允许插件和 skills 向运行时注册工具和 hooks。通过 assembleToolPool()(tools.ts)进行的工具池组装,会合并内置工具与 MCP 提供的工具。获批的 shell 命令会经过 shell 沙箱(shouldUseSandbox.ts),它独立于权限系统来限制文件系统和网络访问。通过 AgentTool(AgentTool.tsx、runAgent.ts)派生子智能体,与所有其他工具一样,经由同一个 buildTool() 工厂分派,以独立隔离的上下文窗口重新进入 queryLoop(),并且只向父级返回一份摘要(第 8 节)。

**状态层(上下文组装、运行时状态、持久化、记忆、侧链)。** 上下文组装是一个带记忆化的状态加载器,而不是路由枢纽:getSystemContext()(context.ts)计算包括 git 状态在内的会话级系统上下文,getUserContext()(context.ts)加载 CLAUDE.md 层级结构和当前日期。两者都被缓存以供重用:系统上下文被追加到系统提示词中,而用户上下文则作为一条用户上下文消息加入。src/state/ 目录管理运行时应用状态。会话转录以大体仅追加的 JSONL 文件形式存储在项目专属路径下(sessionStorage.ts)。CLAUDE.md + 记忆子系统提供一个四级指令层级(claudemd.ts),从受管设置一直到特定目录的文件,另外还有 Claude 在对话过程中写入的自动记忆条目(第 7.2 节)。侧链转录(sessionStorage.ts:247)把每个子智能体的对话存放在单独的文件中,避免子智能体的内容膨胀父级上下文(第 8.3 节)。全局提示词历史保存在 history.jsonl 中(history.ts)。恢复和分叉操作从转录中重建会话状态(conversationRecovery.ts)。

**后端层(执行后端、外部资源)。** 带可选沙箱的 shell 命令执行(BashTool.tsx、PowerShellTool.tsx)、远程执行支持(src/remote/)、跨多种传输变体(包括 stdio、SSE、HTTP、WebSocket、SDK 和特定于 IDE 的适配器)的 MCP 服务器连接(services/mcp/client.ts),以及 src/tools/ 下的 42 个工具子目录,共同实现了具体的工具逻辑。

### 3.4 QueryEngine:一点澄清

QueryEngine.ts 中的类文档写道:"QueryEngine 拥有一次对话的查询生命周期和会话状态。它把 ask() 的核心逻辑提取为一个独立的类,可同时被无头/SDK 路径以及(在未来阶段)REPL 使用。"这个类是面向非交互界面的对话封装,而不是引擎本身。其构造函数接受一个 QueryEngineConfig,包含初始消息、一个中止控制器、一个文件状态缓存以及其他每次对话的状态。它的 submitMessage() 方法是一个异步生成器,负责编排单个回合。共享的查询路径位于 query()(query.ts)中,它封装了一个内部的 queryLoop();QueryEngine 委托给 query()。

这一区分在架构上很重要:交互式 CLI 同样调用 query(),完全绕过 QueryEngine。共享的代码路径是循环函数,而不是引擎类。

### 3.5 权限与安全层

"默认安全"原则通过七个相互独立的层来实现。一个请求必须通过所有适用的层,任何一层都可以阻止它:

1. **工具预过滤(tools.ts):** 被一概拒绝的工具会在任何调用之前就从模型的视野中移除,从而避免模型尝试去调用它们。
2. **默认拒绝的规则评估(permissions.ts):** 拒绝规则始终优先于允许规则,即使允许规则更具体。
3. **权限模式约束(types/permissions.ts):** 当前模式决定了对不匹配任何显式规则的请求的基线处理方式。
4. **自动模式分类器:** 一个基于 ML 的分类器评估工具安全性,有可能拒绝规则系统本会允许的请求。
5. **Shell 沙箱(shouldUseSandbox.ts):** 即使获批,shell 命令仍可能在限制文件系统和网络访问的沙箱中执行。
6. **恢复时不还原权限(conversationRecovery.ts):** 会话范围内的权限在恢复或分叉时不会被还原。
7. **基于 hook 的拦截(types/hooks.ts):** PreToolUse hooks 可以修改权限决定;PermissionRequest hooks 可以与用户对话框并行地异步给出决定(在协调者模式下则先于对话框)。

这些层在第 5 节中有详细描述。

### 3.6 上下文作为瓶颈:超越压缩

除了五层压缩流水线(详见第 7 节)之外,另有若干子系统决策也体现了"上下文即瓶颈"这一约束:

- **CLAUDE.md 懒加载:** 基础的 CLAUDE.md 层级在会话开始时加载,但额外的嵌套目录指令文件和条件规则,只有在智能体读取这些目录中的文件时才会加载,从而避免未使用的指令占用上下文。
- **延迟加载的工具模式:** 当启用 ToolSearch 时,部分工具在初始上下文中只包含其名称;完整的模式(schema)按需加载。
- **子智能体仅返回摘要:** 子智能体只向父级返回摘要文本,而不是其完整对话历史(第 8 节)。
- **每个工具结果的预算:** 单个工具结果被限制在可配置的大小之内,防止某个冗长的输出占用过多上下文。

## 4 回合执行:智能体查询循环

当用户提交"修复 auth.test.ts 中失败的测试"时,输入进入一个反应式(reactive)循环,这是编程智能体几种可能的编排模式之一。本节考察 Claude Code 选择简单 while 循环架构的原因,并端到端地追踪该循环的一个回合,以说明表 1 中的三条设计原则:最小脚手架配合最大运行 harness、将上下文视为稀缺资源并渐进管理,以及优雅恢复与韧性。

### 4.1 查询流水线

每个回合都遵循一个固定的序列(图 2,query.ts):

1. **设置解析。** queryLoop() 函数解构不可变的参数,包括系统提示词、用户上下文、权限回调和模型配置。
2. **可变状态初始化。** 一个单一的 State 对象存储跨迭代的所有可变状态,包括消息、工具上下文、压缩跟踪和恢复计数器。循环的七个继续点("continue sites")各自通过整体赋值来覆盖该对象,而不是逐个字段地修改。
3. **上下文组装。** getMessagesAfterCompactBoundary() 函数检索自上一个压缩边界之后的消息,确保已压缩的内容由其摘要来表示,而不是原始消息。
4. **模型前的上下文整形。** 五个整形器依次执行(第 4.3 节)。
5. **模型调用。** 一个对 deps.callModel() 的 for await 循环以流式方式接收模型响应,传入组装好的消息(前置用户上下文)、完整的系统提示词、思考(thinking)配置、可用工具集、中止信号、当前的模型规格,以及包括快速模式设置、effort 值和回退模型在内的附加选项。
6. **工具调用分派。** 如果响应包含 tool_use 块,它们流向工具编排层(第 4.2 节)。
7. **权限闸门。** 每个工具请求都经过权限系统(第 5 节)。
8. **工具执行与结果收集。** 工具结果作为 tool_result 消息加入对话,循环继续。
9. **停止条件。** 如果响应不含 tool_use 块(仅有文本),则该回合完成。

queryLoop() 函数被定义为一个 AsyncGenerator,在推进过程中产出 StreamEvent、RequestStartEvent、Message、TombstoneMessage 和 ToolUseSummaryMessage 事件。这种基于生成器的设计使得输出可以流式地传给 UI 层,同时在循环内部保持单一的同步控制流。

Claude Code 的反应式循环遵循 ReAct 模式(Yao et al., 2022):模型生成推理和工具调用,harness 执行动作,结果被送入下一次迭代。其他编排模式包括显式的基于图的路由(LangChain, Inc., 2024),其控制流被定义为带类型边的状态机,以及在承诺行动之前探索多条动作轨迹的树搜索方法(Zhou et al., 2023)。Anthropic 自己的文档(Schluntz and Zhang, 2024)识别了五种可组合的工作流模式(提示链、路由、并行化、编排者—工作者,以及评估者—优化者),其中 Claude Code 主要在子智能体委派中使用编排者—工作者模式(第 8 节),同时保持核心循环的反应式特性。反应式设计以搜索的完备性换取简单性和低延迟:每个回合都承诺于一个动作序列,而不回溯。

### 4.2 工具分派与流式执行

当模型响应包含 tool_use 块时,系统在两条执行路径之间选择。主路径使用 StreamingToolExecutor,它在工具从模型响应中流式到达时就开始执行,从而降低多工具响应的延迟。回退路径使用 toolOrchestration.ts 中的 runTools(),它遍历由 partitionToolCalls() 产生的分区。两条路径都将工具分类为并发安全或独占。只读操作可以并行执行,而像 shell 命令这样会修改状态的操作则串行化。

StreamingToolExecutor(StreamingToolExecutor.ts)通过两种协调机制管理并发执行:

- **兄弟中止控制器(Sibling abort controller)。** 当任何一个 Bash 工具出错时触发,立即终止其他正在运行的子进程,而不是让它们运行到结束。
- **进度可用信号(Progress-available signal)。** 当有新输出就绪时,唤醒 getRemainingResults() 的消费者。

结果会被缓冲,并按工具被接收的顺序发出,因此即使工具并行运行,输出顺序也保持不变。这一点很重要,因为模型期望工具结果的顺序与其工具调用请求的顺序一致。这种"并发读、串行写"的执行模型,介于完全串行的分派和更激进的推测式方法(如 PASTE,Sui et al., 2026)之间;PASTE 会在模型仍在生成时,就推测性地预先执行预测的未来工具调用,通过推测来隐藏工具延迟。

工具结果收集阶段遍历来自流式执行器或批处理的 runTools() 异步生成器的更新。两者都是由同一个 for await 循环消费的异步可迭代对象;区别在于工具执行是在模型完成流式输出之前开始(流式),还是在划分为并发安全组之后开始(批处理)。每个更新可能携带一个工具结果、一个附件或一个进度事件。一个特殊检查会检测 hook_stopped_continuation 附件:如果某个 PostToolUse hook 发出信号表示该回合不应继续,就会设置 shouldPreventContinuation 标志。结果通过 normalizeMessagesForAPI() 为 Anthropic API 进行规范化,过滤后只保留用户类型的消息。

### 4.3 模型前的上下文整形器

五个上下文整形器在 query.ts 中于每次模型调用之前依次执行,每个都作用于 messagesForQuery 数组。这五个整形器按顺序运行,较早的步骤先施加较轻的缩减,之后的步骤再施加更广泛的压缩。

**预算缩减(Budget reduction)。**(applyToolResultBudget())对工具结果强制执行每条消息的大小限制,用内容引用替换超大的输出。豁免的工具(maxResultSizeChars 不是有限值的那些)保留其完整输出。对于智能体和会话查询来源,内容替换会被持久化,以便在恢复时重建。预算缩减先于微压缩运行,因为微压缩纯粹按 tool_use_id 运作,从不检查内容;两者可以干净地组合。

**裁剪(Snip)。**(snipCompactIfNeeded(),由 HISTORY_SNIP 控制)一种轻量的修剪,移除较旧的历史片段,返回 {messages, tokensFreed, boundaryMessage}。snipTokensFreed 的值会被传递给自动压缩,因为主 token 计数器是从最近一条助手消息的 usage 字段推导上下文大小的,而这条消息在裁剪后仍然保留着裁剪前的 input_tokens;因此,除非显式传入,否则裁剪节省的量对计数器是不可见的。

**微压缩(Microcompact)。** 细粒度的压缩,始终运行基于时间的路径,并可选地运行感知缓存的路径(由 CACHED_MICROCOMPACT 控制)。当启用缓存路径时,边界消息会被推迟到 API 响应之后,从而可以使用实际的 cache_deleted_input_tokens 而不是估计值。返回 {messages, compactionInfo},其中 compactionInfo 可能包含 pendingCacheEdits。

**上下文折叠(Context collapse)。** 由 CONTEXT_COLLAPSE 控制。这是对对话历史的一种读时投影。源码注释解释道:"不产出任何内容;折叠视图是对 REPL 完整历史的读时投影。摘要消息存放在折叠存储(collapse store)中,而不在 REPL 数组里。这就是让折叠跨回合持久存在的原因。"与其他整形器不同,上下文折叠不会修改 REPL 所存储的历史;它通过 applyCollapsesIfNeeded() 把 messagesForQuery 数组替换为一个投影视图,因此模型看到的是折叠后的版本,而完整历史仍可用于重建。

**自动压缩(Auto-compact)。** 第五个整形器,通过 compact.ts 中的 compactConversation() 触发由模型生成的完整摘要。该函数执行 PreCompact hooks,使用 getCompactPrompt() 创建一个摘要请求,并调用模型来生成压缩后的摘要。结果被送入 buildPostCompactMessages()(compact.ts)。只有当前面四个整形器都运行之后上下文仍然超过压力阈值时,自动压缩才会触发。

### 4.4 恢复机制

查询循环针对若干边缘情况实现了恢复机制:

- **最大输出 token 升级:** 当响应触及输出 token 上限时,系统可以用提高的限制重试,但受一个 GrowthBook 标志控制,并且要求不存在已有的覆盖设置或环境变量上限。每个回合最多允许三次恢复尝试(MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3)。
- **响应式压缩(受 REACTIVE_COMPACT 控制):** 当上下文接近容量上限时,响应式压缩只总结刚好足够腾出空间的部分。hasAttemptedReactiveCompact 标志确保它每回合最多触发一次。
- **提示过长处理:** 如果 API 返回 prompt_too_long 错误,循环首先尝试上下文折叠溢出恢复和响应式压缩。只有在这些都失败之后,它才会以 reason: 'prompt_too_long' 终止。
- **流式回退:** onStreamingFallback 回调处理流式 API 的问题,允许循环以不同的策略重试。
- **回退模型:** fallbackModel 参数使得主模型失败时可以切换到备用模型。

### 4.5 停止条件

多种条件都可以终止循环:

1. **无工具调用:** 模型只产生文本内容(主要的停止条件)。
2. **最大回合数:** 达到可配置的 maxTurns 限制。
3. **上下文溢出:** API 返回 prompt_too_long。
4. **Hook 干预:** 某个 PostToolUse hook 设置了 hook_stopped_continuation。
5. **显式中止:** abortController 信号被触发。

回合流水线决定了工具请求如何被编排和恢复。下一节将考察那道决定每个请求究竟是否被允许执行的闸门。

**图 4** 权限闸门概览与设计原则。

| 原则 | 说明 |
|---|---|
| 渐进式信任(Progressive Trust) | 智能体从最小的自主权开始;用户通过批准那些会成为永久规则的工具调用来扩展自主权。 |
| 默认拒绝、默认询问(Deny-First, Ask-by-Default) | 拒绝规则始终胜出,即使在更宽松的模式下也是如此。在默认和手动批准模式下,未匹配的、带风险的动作会询问用户而不是静默运行;可选的自动模式则通过分类器介导的检查来处理许多此类审查。 |
| 可组合的策略(Composable Policy) | 三种机制共同塑造策略:声明式规则、全局信任模式和可编程 hooks,每种都可独立配置。 |

*(图示:工具调用 → 策略核心[规则、模式、hooks] → 权限判定 → 允许/拒绝/询问 → 执行环境 / 拒绝结果 / 用户或自动分类器。)*

## 5 工具授权与控制边界

生产级编程智能体采用不同的安全架构:分层的策略执行、操作系统级沙箱,或基于版本控制的回滚。Claude Code 结合了前两者,实现了表 1 中的四条设计原则:默认拒绝并升级给人类、渐进式信任谱系、分层机制的纵深防御,以及按可逆性加权的风险评估。

当 Claude 决定执行某个工具时(例如通过 BashTool 运行 npm test 以复现 auth 测试的失败),请求会进入图 4 所示的权限流水线。除了绕过(bypass)模式之外,工具调用都要经过权限系统。在默认的交互姿态下,超出只读访问的动作会请求批准而不是静默运行,而更宽松的模式则用限定范围的自动批准、拒绝或分类器介导的审查来取代部分提示。这一默认设置源自一种有据可查的行为模式:Anthropic 的自动模式分析(Hughes, 2026)发现,用户会批准约 93% 的权限提示,这表明"审批疲劳"使得交互式确认在行为上无法作为唯一的安全机制。由于用户习惯性地不加仔细审查就批准,系统必须独立于人类的警觉性来维持安全。这就是架构上承诺采用默认拒绝评估、一概拒绝的预过滤以及沙箱,作为不依赖用户注意力而运行的独立层的原因。

### 5.1 权限模式与规则评估

类型定义中存在七种权限模式(5 种外部模式位于 types/permissions.ts;auto 有条件地添加;bubble 位于类型联合中):

1. **plan:** 模型必须先制定计划;只有在用户批准后才继续执行。
2. **default:** 标准的交互使用。大多数操作需要用户批准。
3. **acceptEdits:** 工作目录内的编辑以及某些文件系统 shell 命令(mkdir、rmdir、touch、rm、mv、cp、sed)被自动批准;其他 shell 命令需要批准。
4. **auto:** 由基于 ML 的分类器评估未通过快速路径检查的请求(由 TRANSCRIPT_CLASSIFIER 控制)。
5. **dontAsk:** 抑制提示,原本会触发提示的动作被自动拒绝;显式的允许和拒绝规则仍然适用。
6. **bypassPermissions:** 跳过大多数权限提示,但安全关键的检查和免绕过(bypass-immune)规则仍然适用。
7. **bubble:** 仅内部使用的模式,用于将子智能体的权限升级到父终端。

五种对外可见的模式(acceptEdits、bypassPermissions、default、dontAsk、plan)定义在 EXTERNAL_PERMISSION_MODES 数组中。auto 模式只有在 TRANSCRIPT_CLASSIFIER 功能开关启用时才会被有条件地包含。bubble 模式存在于类型联合中,但不在任何一个模式数组里;它在内部用于子智能体的权限升级(第 8 节)。

权限规则按默认拒绝的顺序评估(permissions.ts)。toolMatchesRule() 函数首先检查拒绝规则:拒绝规则始终优先于允许规则,即使允许规则更具体。宽泛的拒绝("拒绝所有 shell 命令")无法被狭窄的允许("允许 npm test")覆盖。规则系统支持工具级匹配(按工具名称)和内容级匹配(匹配特定的工具输入模式,例如 Bash(prefix:npm))。

七种模式构成了一个渐进的自主性谱系,从 plan(用户在执行前批准所有计划),经由 default 和 acceptEdits,直到 bypassPermissions(最少的提示)。这一梯度反映了一个反复出现的设计张力:随着自主性增加,系统必须从交互式批准转向自动化的安全检查。其他智能体系统以不同的方式解决这一张力。SWE-Agent 和 OpenHands(Yang et al., 2024;Wang et al., 2024b)使用 Docker 容器隔离,将智能体的整个执行环境置于沙箱中,而不是评估单个工具调用。Aider(Gauthier, 2024)依赖 Git 作为安全网,使所有更改都可以通过版本控制回退。Claude Code 的做法是在可选的容器沙箱之上叠加多种策略执行机制,以简单性换取对单个动作的细粒度控制。

### 5.2 授权流水线

完整的授权流水线要经过几个阶段:

**预过滤。** 在任何工具请求到达运行时评估之前,filterToolsByDenyRules()(tools.ts)会在工具池组装阶段,把被一概拒绝的工具从模型的视野中彻底剥离。文档指出:"使用与运行时权限检查相同的匹配器,因此像 mcp__server 这样的 MCP 服务器前缀规则,会在模型看到之前就剥离该服务器的所有工具。"这样可以避免模型尝试调用被禁止的工具,从而不会在它们上面浪费调用。

**PreToolUse hook。** 已注册的 hooks 作为权限流水线的一部分被触发。PreToolUse hook 可以返回一个 permissionDecision 以拒绝或询问,或返回一个 updatedInput 来修改工具的输入参数(types/hooks.ts)。hook 的允许并不会绕过后续基于规则的拒绝或安全检查。在交互路径中,用户对话框先入队,hooks 异步运行;协调者(coordinator)及类似的后台智能体路径则会在显示对话框之前先等待自动化检查。

**规则评估。** 默认拒绝的规则引擎评估该请求。MCP 工具按其完全限定的 mcp__server__tool 名称匹配,服务器级规则匹配该服务器的所有工具。

**权限处理器。** useCanUseTool.tsx 中的处理器根据运行时上下文分支进入四条路径之一:

1. **协调者(Coordinator):** 用于多智能体协调模式。在回退到用户交互之前,先尝试自动化解决(分类器、hooks、规则)。
2. **群体工作者(Swarm worker):** 处理多智能体群体(swarm)中拥有各自解决逻辑的工作者智能体。
3. **推测式分类器(Speculative classifier):** 当启用 BASH_CLASSIFIER 且工具是 BashTool 时,推测式分类器让一个预先启动的分类结果与一个超时进行竞速。如果分类器以高置信度返回,该工具会被立即批准而无需用户交互。
4. **交互式(Interactive):** 回退路径。通过终端 UI 呈现标准的用户批准对话框。

在协调者和某些后台路径中,会在用户交互之前先尝试自动化解决。在标准的交互路径中,对话框可以先出现,而 hooks 或分类器检查并行继续。

当分类器或拒绝规则阻止某个动作时,系统把这次拒绝视为一种路由信号,而非硬性终止:模型会收到拒绝的原因,修正其方法,并在下一次循环迭代中尝试更安全的替代方案。PermissionDenied hook 事件(第 6 节)使外部代码能够以编程方式观察并响应这些拒绝。这种以恢复为导向的设计意味着,权限强制执行是在塑造智能体的行为,而不是简单地让它停下来。

### 5.3 自动模式分类器与 Hook 生命周期

自动模式分类器(yoloClassifier.ts)在启用时参与权限决策。当启用 TRANSCRIPT_CLASSIFIER 时,分类器会加载三种提示资源:

- 一个基础系统提示词;
- 一个外部权限模板;
- 对于 Anthropic 内部用户,一个单独的内部模板。

分类器对照对话转录和权限模板评估拟议的工具调用,产生允许、拒绝或请求手动批准的结果。isUsingExternalPermissions() 函数检查 USER_TYPE 和一个 forceExternalPermissions 配置标志,以选择合适的模板。

在源码中定义的 27 个 hook 事件(coreTypes.ts)中,有五个直接参与权限流程,每个都带有特定的、经 Zod 校验的输出模式(types/hooks.ts):

- **PreToolUse:** 可以返回 permissionDecision(拒绝或询问,但"允许"不会绕过后续检查)、permissionDecisionReason 以及 updatedInput(修改参数)。
- **PostToolUse:** 可以注入 additionalContext,并且对于 MCP 工具,可以返回 updatedMCPToolOutput,在结果进入上下文之前修改它。
- **PostToolUseFailure:** 可以注入 additionalContext,提供针对特定错误的指导。
- **PermissionDenied:** 可以在自动模式拒绝之后提供重试指导。
- **PermissionRequest:** 可以返回允许或拒绝的决定。在协调者及类似路径中,这可以在用户对话框之前就解决;在标准的交互路径中,它也可以与对话框并行运行。

对于非 MCP 工具,tool_result 在 PostToolUse hook 触发之前就已发出。对于 MCP 工具,结果会被延迟到后置 hooks 运行之后,使 updatedMCPToolOutput 得以生效。

### 5.4 Shell 沙箱

Shell 沙箱为 Bash 和 PowerShell 命令提供了额外的保护层(shouldUseSandbox.ts)。shouldUseSandbox() 函数检查沙箱是否全局启用、该调用是否已选择退出,以及命令是否匹配任何排除模式。

启用后,沙箱提供独立于应用级权限模型的文件系统和网络隔离。³ 一个命令可以获得权限批准但仍被沙箱化,也可以被权限拒绝而从未到达沙箱检查。这两个系统运作于不同的轴线上:授权与隔离。

> ³ 独立的安全研究报告称,在所分析的时间窗口内,这种网络限制存在一个解析器差异(parser-differential)缺口:主机允许列表使用 JavaScript 的后缀匹配,而名称解析会在嵌入的空字节处截断,因此精心构造的主机名可以通过后缀检查,却解析到另一个被阻止的主机。报告的受影响范围(v2.0.24–v2.1.89)包含此处分析的 v2.1.88 快照,且未分配 CVE(Cyber Security News, 2026)(C 级证据)。

分层安全架构建立在一个独立性假设之上:如果某一层失效,其他层会捕获违规。然而,若干层共享共同的性能约束。安全研究人员(Adversa.ai, 2026)记录到,包含超过 50 个子命令的命令,会回退到单一的通用批准提示,而不是逐个子命令地运行拒绝规则检查,因为逐子命令的解析曾导致 UI 卡顿。这个例子表明,当各层共享失效模式时,纵深防御可能退化,这是安全与性能之间的一种结构性张力,将在第 12.3 节中进一步分析。

权限流水线决定一个工具请求是否执行。下一节考察首先由什么决定哪些工具存在:即组装模型动作面的扩展性架构。

## 6 扩展性:MCP、插件、Skills 与 Hooks

编程智能体反复出现的一个设计问题是如何构造扩展面:单一统一的机制、少量专门化的机制,还是具有不同上下文成本的分层堆栈。这里的分析说明了表 1 中的两条设计原则:可组合的多机制扩展性,以及外部化的可编程策略。回到运行示例:一旦 Claude 在尝试修复 auth.test.ts,并且先前的 npm test 请求已由权限系统调解(第 5 节),下一个问题就是修复工作有哪些由扩展带来的动作面可用。当 Claude Code 中一个回合开始时,模型看到的不仅有 BashTool 和 FileReadTool 这样的内置工具,还有来自某个 MCP 服务器的数据库查询工具、来自 .claude/skills/ 的自定义 lint skill,以及已安装插件所贡献的工具。它们通过四种在循环不同位置扩展智能体的机制到来:MCP 服务器提供外部工具集成,插件打包并分发组件集合,skills 注入特定领域的指令,而 hooks 拦截工具执行的生命周期。Anthropic 的文档(Anthropic, 2026f)提出了更宽泛的视角,在这里分析的四种机制之外还包括 CLAUDE.md(第 7 节)和子智能体(第 8 节)。我们把 CLAUDE.md 和子智能体放在各自的章节中处理,因为它们运作于不同的子系统(分别是上下文构建和委派),但上下文成本的排序在架构上意义重大:它揭示了每个扩展点如何在表达能力与有限的上下文窗口之间做权衡。

### 6.1 四种扩展机制

这些机制在不同的源码目录中实现(图 5),服务于不同的集成模式:

**MCP 服务器。** 模型上下文协议(Model Context Protocol)是外部工具集成的主要路径。MCP 服务器从多个作用域配置:项目、用户、本地和企业,另有插件和 claude.ai 服务器在运行时合并(services/mcp/config.ts)。MCP 客户端(services/mcp/client.ts)支持多种传输类型:stdio、SSE、HTTP、WebSocket、SDK,以及特定于 IDE 的变体(sse-ide、ws-ide)和内部的 claudeai-proxy。每个已连接的服务器以 MCPTool 对象的形式贡献工具定义。专用的内置工具 ListMcpResourcesTool 和 ReadMcpResourceTool 提供对 MCP 资源的访问。

**图 5** Claude Code 的扩展机制接入智能体循环的位置。左侧的伪代码是图 1 中"智能体循环"块的放大。每个智能体循环都有三个注入点:**a** assemble() 控制模型看到什么,**b** model() 控制它能触及什么,**c** execute() 控制一个动作是否以及如何真正运行。

```
# Claude Code 智能体循环的一个回合
while not stopped:
    # a assemble:构建模型看到的内容
    context = assemble(
        system_prompt,   # 指令头部
        tool_schemas,    # 可调用工具的签名
        history,         # 先前回合的消息
        hook_additions,  # 由 hooks 推入的内容
    )
    # b model:选择下一个动作
    action = model(context, tools)   # 扁平的工具池
    if action.is_text_only():
        stopped = run_stop_hooks(action)   # 可能否决
        continue
    # c execute:授权并运行工具调用
    action, hook_decision = run_pre_tool_hooks(action)
    if not permitted(action, hook_decision):
        continue
    result = execute(action)                # 工具在此运行
    result = run_post_tool_hooks(result)    # 修改/标注
    history.append(action, result)
```

**a assemble():模型看到什么**

| 元素 | 作用 |
|---|---|
| CLAUDE.md 文件 | 载入上下文;工作目录之上的文件在启动时加载,子目录文件按需加载 |
| Skill 描述 | 向模型宣告可用的 skills,以便它调用 SkillTool |
| MCP 资源与提示 | MCP 服务器推送的非工具内容 |
| 输出风格(Output style) | 替换响应格式化的系统块 |
| UserPromptSubmit hook | 在每个用户回合注入上下文,或阻止 |
| SessionStart hook | 会话开始时一次性注入上下文 |

**b model():模型能触及什么**

| 元素 | 作用 |
|---|---|
| 内置工具 | Read / Edit / Bash / ……,随 CLI 一起发布 |
| MCP 工具 | 来自任何 MCP 服务器的工具,位于同一个扁平池中 |
| SkillTool | 按名称启动 skill 的元工具(meta-tool) |
| AgentTool | 递归派生子智能体的元工具 |

**c execute():一个动作是否/如何运行**

| 元素 | 作用 |
|---|---|
| 权限规则 | 对每次调用的声明式允许 / 拒绝 / 询问 |
| PreToolUse hook | 批准 / 阻止 / 改写工具调用 |
| PostToolUse hook | 在调用之后修改输出或注入上下文 |
| Stop hook | 在模型停止时强制循环继续 |
| SubagentStop hook | 同上,针对通过 AgentTool 派生的子智能体 |
| Notification hook | 针对用户通知的外部副作用 |

**插件(Plugins)。** 插件扮演双重角色:它们既是一种打包格式,也是一种分发机制。PluginManifestSchema(utils/plugins/schemas.ts)接受十种组件类型:命令、智能体、skills、hooks、MCP 服务器、LSP 服务器、输出风格、通道(channels)、设置以及用户配置。插件加载器(utils/plugins/pluginLoader.ts)校验清单,并将每个组件路由到各自的注册表:命令和 skills 通过 SkillTool 元工具呈现,智能体出现在 AgentTool 所使用的定义中,hooks 合并进 hook 注册表,MCP 和 LSP 服务器并入其标准配置,而输出风格则修改响应格式。因此,单个插件包可以同时在多种组件类型上扩展 Claude Code,使插件成为第三方扩展的主要分发载体。

**Skills。** 每个 skill 由一个带 YAML frontmatter 的 SKILL.md 文件定义。parseSkillFrontmatterFields() 函数(loadSkillsDir.ts)解析 15 个以上的字段,包括显示名称、描述、允许的工具(授予该 skill 访问额外工具的权限)、参数提示、模型覆盖、执行上下文('fork' 表示隔离执行)、关联的智能体定义、effort 级别以及 shell 配置。Skills 可以定义自己的 hooks,这些 hooks 在调用时动态注册。内置的 skills 在启动时于内存中注册。被调用时,SkillTool 元工具会把该 skill 的指令注入上下文。

**Hooks。** 源码定义了 27 个 hook 事件,涵盖工具授权(PreToolUse、PostToolUse、PostToolUseFailure、PermissionRequest、PermissionDenied)、会话生命周期(SessionStart、SessionEnd、Setup、Stop、StopFailure)、用户交互(UserPromptSubmit、Elicitation、ElicitationResult)、子智能体协调(SubagentStart、SubagentStop、TeammateIdle、TaskCreated、TaskCompleted)、上下文管理(PreCompact、PostCompact、InstructionsLoaded、ConfigChange)、工作区事件(CwdChanged、FileChanged、WorktreeCreate、WorktreeRemove)以及通知(coreTypes.ts、coreSchemas.ts)。其中 15 个拥有特定事件的输出模式,字段丰富,支持权限决策、上下文注入、输入修改、MCP 结果转换和重试控制(types/hooks.ts)。通过设置和插件配置的持久化 hook 命令使用四种命令类型:shell 命令(type: command)、LLM 提示 hook(type: prompt)、HTTP hook(type: http)以及智能体式验证器 hook(type: agent)(schemas/hooks.ts)。运行时还额外支持由 SDK 和内部埋点使用的不可持久化回调 hook(type: callback)(types/hooks.ts)。Hook 的来源包括启动时的 settings.json、插件和受管策略;skill 的 hooks 在调用时动态注册(utils/hooks.ts)。五个工具授权事件在第 5.3 节中有详细说明。

### 6.2 工具池组装

tools.ts 中的 assembleToolPool() 函数在源码注释中被描述为"合并内置工具与 MCP 工具的唯一事实来源"。该组装遵循一条五步流水线:

1. **基础工具枚举。** getAllBaseTools()(tools.ts)返回最多 54 个工具的数组:其中 19 个始终包含(如 BashTool、FileReadTool、AgentTool、SkillTool),另外 35 个根据功能开关、环境变量和用户类型有条件地包含。Anthropic 内部用户会获得额外的内部工具。工作树(worktree)模式启用 EnterWorktreeTool 和 ExitWorktreeTool。智能体群体(swarm)启用团队工具。当 Bun 二进制文件中提供内嵌的搜索工具时,专用的 GlobTool 和 GrepTool 会被省略。
2. **模式过滤。** getTools()(tools.ts)应用特定模式的过滤。在 CLAUDE_CODE_SIMPLE 模式下,只有 Bash、Read 和 Edit 可用(在 REPL 分支中则是 REPLTool;如适用还有协调者工具)。每个工具的 isEnabled() 方法会被调用,以检查运行时可用性。
3. **拒绝规则预过滤。** filterToolsByDenyRules()(tools.ts)在任何调用之前,把被一概拒绝的工具从模型的视野中剥离。
4. **MCP 工具集成。** 来自 appState.mcp.tools 的 MCP 工具经拒绝规则过滤后,与内置工具合并。
5. **去重。** 工具按名称去重,内置工具优先于 MCP 工具。

REPL.tsx(通过 useMergedTools hook)和 AgentTool.tsx(在构建工作者工具集时)都会调用此函数,从而确保所有执行路径上的组装保持一致。在请求时,被延迟的工具可能会对模型的上下文隐藏,直到通过 ToolSearch 被显式查询(tools.ts)。

基于智能体的扩展(通过 .claude/agents/*.md 的自定义智能体定义,以及插件贡献的智能体)在第 8 节中介绍,因为智能体与上述四种机制有根本不同:它们创建新的、隔离的上下文窗口,而不是扩展当前的窗口。

### 6.3 为什么是四种机制?

鉴于每增加一种扩展机制,开发者就要多学一块内容,一个自然的问题是:为什么 Claude Code 使用四种不同的机制,而不是整合为一两种。答案在于这样一个观察:不同类型的扩展性给上下文窗口带来不同的成本,而单一机制无法在"零上下文的生命周期 hooks"到"重模式的工具服务器"的整个范围内,既覆盖全貌,又不迫使扩展作者做出不必要的权衡。

**表 2** 每种扩展机制独有的能力。上下文成本指该机制在激活时消耗有限上下文窗口的多少。

| 机制 | 独有能力 | 上下文成本 | 插入点 |
|---|---|---|---|
| MCP 服务器 | 外部服务集成(多种传输) | 高(工具模式) | model():工具池 |
| 插件 | 多组件打包 + 分发 | 中(视情况而定) | 全部三个点 |
| Skills | 特定领域指令 + 元工具调用 | 低(仅描述) | assemble():上下文注入 |
| Hooks | 生命周期拦截 + 事件驱动自动化 | 默认为零 | execute():工具调用前/后 |

如表 2 所总结,每种机制都以部署复杂度换取一种不同类型的扩展性。MCP 服务器提供运行时工具集成(模型获得新的可调用工具),代价是服务器管理开销以及被工具模式消耗的上下文预算。Skills 塑造智能体如何思考(而不仅仅是它拥有什么工具),上下文成本极低,因为只有 frontmatter 描述(而非完整内容)留在提示词中。Hooks 提供横切的生命周期控制(阻止、改写或标注工具调用),默认不占用上下文,尽管 hooks 也可以选择注入额外的上下文。插件把其他三者的任意组合打包成可分发的包,充当打包和分发层,而不是一个独立的运行时原语。这种分级的上下文成本排序(hooks 为零、skills 为低、插件为中、MCP 为高)意味着廉价的扩展可以大规模扩展而不会耗尽上下文窗口,而昂贵的扩展则留给真正需要新工具面的情形。

一些智能体框架提供单一的扩展机制,通常是仅限工具的 API,所有定制都以额外的可调用工具的形式到来。另一些使用两层,将工具与配置或指令注入分开。Claude Code 的四机制方法可以容纳更广泛的扩展模式,从零上下文的事件处理器到完整的外部服务集成,但这也提高了开发者在为某个集成任务选择用哪种机制时面临的学习曲线。

## 7 上下文构建与记忆

智能体如何管理其上下文窗口并持久化用户指令,是一项核心的设计选择;不同的系统在基于文件的透明性、基于数据库的检索以及不透明的学习表示之间做出选择。这里的设计选择体现了表 1 中的两条原则:将上下文视为稀缺资源并渐进管理,以及透明的基于文件的配置与记忆。

到运行示例的这一步,任务已经积累了状态:最初的请求、npm test 的权限结果、第 6 节中组装的工具池,以及迄今为止收集到的所有文件读取或命令输出。本节探讨在下一次模型调用之前,这些不断增长的状态是如何被打包进 Claude Code 有限的上下文窗口的。

在模型被调用之前,智能体循环会从工具池(第 6 节)、CLAUDE.md 文件、自动记忆和对话历史中组装出一个上下文窗口。以下小节涵盖组装顺序、CLAUDE.md 层级结构以及多步压缩流水线。

**图 6** 上下文构建与记忆层级。汇聚到上下文窗口的来源包括系统提示词、输出风格、环境信息、CLAUDE.md 层级(从受管级到特定目录级)、自动记忆、路径限定规则、MCP 工具名称、通过 ToolSearch 延迟加载的工具定义、对话历史、文件读取、命令输出、工具结果、子智能体摘要和压缩摘要。

| 层 | 内容 | 加载时机 | 访问方式 |
|---|---|---|---|
| (1) 系统层 | 系统提示词、环境信息、输出风格、Skill 描述、MCP 工具名称 | 启动时 | 只读 |
| (2) 项目配置 | CLAUDE.md 层级(5 级:受管 → 操作系统 → 项目 → .claude/ → 本地 → 特定目录)、路径限定规则(.claude/rules/*) | 启动时 / 懒加载 | 热重载 |
| (3) 记忆 | 自动记忆、压缩摘要(替换冗长的历史) | 启动时 | 系统写入 |
| (4) 对话 | 对话历史、子智能体摘要 | 逐回合累积(向前携带) | 追加 |
| (5) 运行时 | 读取的文件、命令输出、工具结果 | 执行期间添加(向前携带) | 由模型触发 |
| (6) 按需 | 延迟加载的工具定义(仅在需要时才加载完整模式) | 通过 ToolSearch 按需 | 懒加载 |

> 可变性随层级递增:(1)(2)(3) 在启动时加载 → (4) 每回合累积 → (5) 在执行期间添加 → (6) 通过 Tool Search 按需加载。

### 7.1 上下文窗口组装

上下文窗口(图 6)由以下来源组装而成,其中一些在初始组装时加入,另一些则在回合进行中较晚注入:

1. **系统提示词**,包含输出风格的修改以及任何 --append-system-prompt 标志的内容。
2. **环境信息**,通过 getSystemContext()(context.ts)获得:git 状态(在远程模式或禁用 git 指令时跳过),以及一个面向内部构建的可选缓存破坏注入(由 BREAK_CACHE_COMMAND 控制)。每个会话记忆化一次。
3. **CLAUDE.md 层级**,通过 getUserContext()(context.ts)获得:四级指令文件层级(第 7.2 节)。同样被记忆化。
4. **路径限定规则:** 条件性的、与目录匹配的规则,在智能体读取匹配目录中的文件时懒加载。
5. **自动记忆:** 与上下文相关的记忆条目,被异步预取。
6. **工具元数据:** skill 描述、MCP 工具名称,以及延迟加载的工具定义(通过 ToolSearch,按需)。
7. **对话历史:** 向前携带,受压缩影响。
8. **工具结果:** 文件读取、命令输出、子智能体摘要。
9. **压缩摘要:** 替换较旧的历史片段。

query.ts 中的系统提示词组装,通过 asSystemPrompt(appendSystemContext(systemPrompt, systemContext))() 将系统上下文与基础提示词组合起来。用户上下文(CLAUDE.md 和日期)则通过 prependUserContext() 被前置到消息数组中。这种分离意味着 CLAUDE.md 的内容在 API 请求中占据与系统提示词不同的结构位置,这可能会影响模型的注意力模式。

若干上下文来源是在主窗口构建之后较晚注入的:相关记忆的预取(query.ts)、MCP 指令增量(仅新增或变更的服务器指令)、智能体列表增量,以及后台智能体的任务通知。因此,上下文窗口在组装时并非静态,而是可以在回合中增长。

### 7.2 CLAUDE.md 层级与自动记忆

有一条设计原则塑造了记忆系统:存储的上下文应当可被用户检查和编辑。CLAUDE.md 文件是纯文本 Markdown,而不是结构化配置或不透明的数据库条目。这一透明性选择以表达能力换取可审计性:用户可以直接检查和编辑自己控制的记忆文件,项目级记忆也可以与代码库一起进行版本控制(Anthropic, 2026g;MindStudio Team, 2026)。其他记忆架构说明了这种权衡。检索增强的方法使用基于嵌入的查找来呈现相关的先前上下文,获得了灵活性,但代价是可检查性:用户难以轻易看到或编辑检索系统认为相关的内容。基于数据库的记忆提供结构化查询,但需要额外的基础设施,并且对版本控制不透明。Claude Code 基于文件的方法使这些记忆面可读可编辑,尽管其他上下文来源仍然通过系统提示词、工具、hooks、MCP 服务器和运行时状态进入。系统不使用嵌入或向量相似度索引来检索记忆;相反,它使用基于 LLM 的记忆文件头部扫描,按需选择最多五个相关文件,并以文件粒度而非条目粒度呈现它们。基于嵌入的系统可以更有选择性地检索单个条目,代价是可检查性以及维护索引所需的基础设施。

CLAUDE.md 文件遵循多级加载层级。源码头部(claudemd.ts)定义了四种记忆类型:

1. **受管记忆(Managed memory)**(例如 Linux 上的 /etc/claude-code/CLAUDE.md):面向所有用户的操作系统级策略。
2. **用户记忆(User memory)**(~/.claude/CLAUDE.md):私有的全局指令。
3. **项目记忆(Project memory)**(项目根目录中的 CLAUDE.md、.claude/CLAUDE.md 和 .claude/rules/*.md):提交到代码库中的指令。
4. **本地记忆(Local memory)**(项目根目录中的 CLAUDE.local.md):被 git 忽略,用于私有的、特定于项目的指令。

文件发现过程从当前目录向上遍历到根目录,在每个目录中检查所有项目记忆和本地记忆文件。离当前目录越近的文件优先级越高(加载得越晚)。

文件按"优先级的反序"加载:较晚加载的文件会获得模型更多的注意力。对于从根目录到当前工作目录(CWD)的目录,.claude/rules/*.md 中的无条件规则在启动时急切加载。对于 CWD 之下的嵌套目录,即使是无条件规则也是在智能体读取匹配目录中的文件时才懒加载。这意味着模型的指令集可以在对话期间随着代码库中新部分被探索而演化。

CLAUDE.md 的内容是作为用户上下文(一条用户消息)传递的,而不是作为系统提示词内容(context.ts)。这一架构选择有重要的含义:由于 CLAUDE.md 的内容是作为对话上下文而非系统级指令传递的,模型对这些指令的遵从是概率性的,而非有保证的。按默认拒绝顺序评估的权限规则(第 5 节)则提供确定性的强制执行层。这就在指导(CLAUDE.md,概率性)与强制执行(权限规则,确定性)之间形成了有意的分离。该函数调用 setCachedClaudeMdContent() 来缓存已加载的内容,供自动模式分类器使用,以避免 CLAUDE.md 加载器与权限系统之间产生导入循环。

记忆文件支持 @include 指令,用于模块化的指令集(claudemd.ts 中的 processMemoryFile())。语法变体包括 @path、@./relative、@~/home 和 @/absolute。该指令只在叶子文本节点中有效(不在代码块内)。在实现中,包含者文件先被推入,被包含的文件追加在其后,通过跟踪已处理的路径来防止循环引用,不存在的文件则被静默忽略。

### 7.3 压缩流水线

五层压缩流水线(第 4.3 节)通过分级压缩(query.ts)实现了"上下文即瓶颈"原则。Claude Code 不是采用单一策略,而是依次应用五层,每一层的激进程度递增(其中三层受功能开关控制;预算缩减始终启用,而自动压缩可由用户配置)。这种分级方法与更简单的替代方案形成对比,例如单遍截断(丢弃最旧的消息)或单一的摘要步骤。分级设计体现了一种"懒降级"原则:先应用破坏性最小的压缩,只有当更廉价的策略不足时才升级。这种方法的代价是复杂性。五个相互作用的压缩层(其中若干由功能开关控制)产生了用户难以完全预测的行为。自动压缩会在转录中生成可见的摘要,微压缩会发出边界标记,但上下文折叠运行时没有用户可见的输出。更简单的单遍方法会牺牲信息,但更容易推理。

1. **预算缩减**(始终启用):每个工具结果的大小限制。
2. **裁剪**(HISTORY_SNIP):轻量级的旧历史修剪。
3. **微压缩**(CACHED_MICROCOMPACT):细粒度、感知缓存的压缩。
4. **上下文折叠**(CONTEXT_COLLAPSE):对历史的读时虚拟投影。
5. **自动压缩**(默认启用,可禁用):由模型生成的完整摘要。

buildPostCompactMessages() 函数(compact.ts)返回如下压缩后的输出结构:[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]。边界标记通过 annotateBoundaryWithPreservedSegment() 带上保留片段的元数据,记录 headUuid、anchorUuid 和 tailUuid,以支持读时链条修补。这种以追加为主的设计意味着压缩从不修改或删除先前写入的转录行;它只追加新的边界事件和摘要事件。

压缩函数 compactConversation()(compact.ts)包含若干设计选择。Pre-compact hooks 首先触发,允许由 hook 注入自定义指令。一个 GrowthBook 功能开关控制压缩路径是否复用主对话的提示缓存(一条代码注释记录了 2026 年 1 月的一次实验:"false 路径有 98% 的缓存未命中,约占整个集群 cache_creation 的 0.76%")。压缩之后,附件构建器会根据实时的应用状态重新宣告运行时状态(计划、skills 和异步智能体),因为压缩会丢弃先前的附件消息,但不会丢弃底层状态。

当系统把工作委派给各自运行在有限上下文窗口中的子智能体时,上下文隔离变得更加关键。

## 8 子智能体委派与编排

多智能体编排是编程智能体的一个关键设计维度,其选择涵盖父子层级结构、基于对等对话的框架(Wu et al., 2024)以及图结构的工作流引擎(LangChain, Inc., 2024)。Claude Code 的委派架构实现了表 1 中的"隔离的子智能体边界"原则,同时兼有"默认拒绝并升级给人类"(权限覆盖)和"按可逆性加权的风险评估"(子智能体工具限制)的方面。

当 Claude 判定修复 auth 测试需要先探索认证模块的结构时,它可以把这项探索委派给一个子智能体。委派机制是 Agent 工具(AgentTool.tsx),Task 作为遗留别名保留。模型以结构化的输入调用 Agent,输入包括委派提示词、可选的子智能体类型,以及隔离模式、权限覆盖和工作目录的配置。

### 8.1 Agent 工具与委派标准

Agent 工具的输入模式(图 7)使用受功能开关控制的字段,当其对应的功能被禁用时,省略可选参数。isolation 字段对内部用户提供 ['worktree', 'remote'],对外部用户提供 ['worktree'],在构建时确定。cwd 字段由一个功能开关控制。当后台任务被禁用,或启用了 fork-subagent 模式时,run_in_background 字段会被省略。

Claude Code 根据功能开关和入口点,提供最多六种内置子智能体类型:

- **Explore:** 主要面向读取/搜索的调查,其拒绝列表中包含写入和编辑工具。
- **Plan:** 创建结构化计划;执行通过标准的权限模型进行。
- **General-purpose(通用):** 能力广泛,在被显式请求时使用(注意:省略类型可能会路由到 fork-subagent 路径,该路径复用父级的对话上下文而不是隔离它)。
- **Claude Code Guide:** 上手引导和文档协助,带有其自己的 permissionMode 覆盖。
- **Verification(验证):** 运行验证检查(测试套件、lint)。
- **Statusline-setup:** 专用于终端状态栏配置。

除了内置类型之外,用户可以通过 .claude/agents/*.md 文件定义自定义子智能体,插件则通过 loadPluginAgents.ts 贡献智能体定义。每个文件的 markdown 正文充当该智能体的系统提示词,YAML frontmatter 指定配置字段,包括描述、工具(允许列表)、disallowedTools、模型、effort、permissionMode、mcpServers、hooks、maxTurns、skills、记忆作用域、后台标志和隔离模式。JSON 格式的智能体定义支持相同的字段,另外还有 prompt 作为一个显式字段(loadAgentsDir.ts)。这意味着一个自定义智能体可以是一个完整配置的、隔离的子系统,拥有自己的工具、模型、权限、hooks、记忆作用域和隔离模式。AgentTool 与 SkillTool 并列于基础工具池中,作为分派到这些定义的元工具,但两者有根本区别:SkillTool 通常把指令注入当前的上下文窗口(带有一个可选择启用的 context: fork 模式,通过同一套 runAgent() 机制派生隔离的子智能体),而 AgentTool 总是派生一个新的、隔离的子智能体。其代价是,大多数子智能体调用需要一个自包含的提示词,因为默认路径不继承父级的对话历史(fork-subagent 路径是例外)。共享完整转录历史的基于对话的框架避免了这一成本,但随着智能体数量增加,有上下文爆炸的风险。

**图 7** 子智能体隔离与委派架构。Agent 工具分派给内置子智能体(Explore、Plan、通用)或自定义子智能体,每个都在隔离的上下文中运行,带有重建的权限上下文和独立的工具集。Agent 工具沿三个轴分派:路由(队友/teammate)、隔离(远程、工作树)和生命周期(异步、同步)。

*(图示:主对话 → [委派] → Agent(Task = 遗留别名)→ 内置类型:Explore、Plan、通用、自定义,以及其他内置工具(状态栏、验证)→ 隔离沙箱,每个子智能体的上下文相互隔离:① 重建的权限上下文与工具集 ② 权限模式覆盖(可选)③ 隔离的工作树 → 子智能体转录(.jsonl + meta.json)→ 子智能体报告(文本 + 元数据)→ 插入结果回到主转录。)*

### 8.2 隔离架构

子智能体隔离支持多种模式(AgentTool.tsx):

- **Worktree(工作树):** 创建一个临时的 git 工作树,让子智能体拥有自己的仓库副本进行修改,而不影响父级的工作树。
- **Remote(远程,仅限内部):** 在远程的 Claude Code Remote 环境中启动,始终在后台运行。
- **In-process(进程内,默认):** 与父级共享文件系统,但在隔离的对话上下文中运行。

子智能体的权限覆盖逻辑(runAgent.ts)涉及若干具体规则。当子智能体定义了 permissionMode 时,除非父级已处于 bypassPermissions、acceptEdits 或 auto 模式,否则就会应用该覆盖,因为这些模式总是优先,它们代表了用户对安全/自主性权衡作出的明确决定。对于异步智能体,系统通过一个级联来决定是否避免提示:首先是显式的 canShowPermissionPrompts,然后是 bubble 模式(始终显示,因为它们升级到父终端),最后是默认值(同步智能体显示提示,异步智能体不显示)。能够显示提示的后台智能体会设置 awaitAutomatedChecksBeforeDialog: true,确保分类器和 hooks 在打断用户之前先完成解决。

这些隔离模式占据了设计空间中的不同点。基于容器的隔离(SWE-Agent 和 OpenHands 所使用,Yang et al., 2024;Wang et al., 2024b)提供更强的资源边界,但需要容器基础设施。仅上下文的隔离(由 AutoGen 等基于对话的框架使用,Wu et al., 2024)共享文件系统,但分离对话历史。Claude Code 基于工作树的隔离,利用 Git 的内置机制,在不引入容器编排的前提下提供工作区级别的文件系统分离。

当 allowedTools 被显式提供给 runAgent()(runAgent.ts)时,适用一个两层的权限作用域模型。来自 --allowedTools 的 SDK 级权限被保留:"来自 SDK 使用者的、应适用于所有智能体的显式权限。"但会话级规则会被子智能体声明的 allowedTools 所取代。当没有提供 allowedTools 时(常见的 AgentTool 路径),父级的会话级规则会被继承而不被替换。

### 8.3 侧链转录

每个子智能体将自己的转录写入一个单独的 .jsonl 文件,并附带一个 .meta.json 元数据文件(sessionStorage.ts、runAgent.ts)。这种侧链设计意味着子智能体的历史被保留下来用于调试和审计,但不会膨胀父级的会话文件。只有子智能体的最终响应文本和元数据返回到父级对话上下文;完整的子智能体历史从不进入父级的上下文窗口,这遵循了"上下文即瓶颈"原则。

仅返回摘要的模型是一种有意的上下文节约选择:在智能体之间共享完整转录历史的基于对话的框架,随着智能体数量增加,有上下文爆炸的风险。即使是隔离上下文的并行也带来可观的成本。Claude Code 的智能体团队在计划模式下消耗的 token 约为标准会话的 7 倍(Anthropic, 2025b),这使得当子智能体同样处于隔离上下文中时,仅返回摘要就更为关键。

对于智能体团队中的多实例协调,harness 使用文件锁,而不是消息代理或分布式协调服务(Anthropic, 2025b)。每个队友都有自己的收件箱 JSON 文件(utils/teammateMailbox.ts);任务分配和其他智能体间消息在每个收件箱的锁文件(utils/lockfile.ts)保护下被推入接收者的收件箱,文件存放在可预测的文件系统路径上。这以吞吐量换取了两个属性:零依赖部署(无需外部基础设施)以及完全可调试性(任何智能体的状态都可以通过读取纯文本 JSON 文件来检查)。

## 9 会话持久化与恢复

编程智能体中的会话持久化涉及在仅追加日志、结构化数据库、基于检查点的快照和无状态架构之间的设计选择,它们在可审计性、查询能力和部署复杂度上各有不同的权衡。Claude Code 的持久化设计实现了表 1 中的"仅追加的持久状态"原则。会话范围的权限只存在于内存中,不会被序列化到转录里,因此恢复时会根据 CLI 参数和磁盘设置重建权限上下文;任何重建后的上下文不能识别的请求,都会回退到默认拒绝式的提示。

当 auth 测试任务进行到本节时,会话中已包含最初的提示词、工具调用与结果、压缩边界,以及来自探索认证模块的子智能体摘要(第 8 节)。本节探讨这些产物中哪些被持久记录,以及在不沿用会话旧权限授予的情况下,事后可以恢复什么。

**图 8** 会话持久化与上下文压缩。该图把实时的会话状态(上下文窗口、压缩)与持久存储(会话转录、history.jsonl、子智能体侧链、检查点)分开。恢复(resume)和分叉(fork)会还原消息,但不会还原会话范围的权限。

| 原则 | 说明 |
|---|---|
| 对话比上下文更长久(Conversations Outlive Context) | 会话的有效寿命不能受模型上下文窗口所限。磁盘上的转录记录持久的会话事件,因此压缩可以回收实时视图,而无需结束对话。 |
| 对话会超出单一路径(Conversations Outgrow a Single Path) | 会话不应被困在单一的线性轨迹上。仅追加的转录让用户可以回退、恢复,或分叉成新的分支,而不丢失先前的工作。 |

*(图示:接近容量时触发压缩流程:① 移除旧的工具输出 → ② 生成会话摘要 → ③ 标记压缩边界;持久存储包括会话转录 .jsonl、历史/子智能体日志;检查点支持回退、恢复、分叉。)*

Claude Code 的持久化机制会在事件发生时,将对话(消息、工具结果和压缩边界)写入磁盘。

### 9.1 转录模型

会话转录以大体仅追加的 JSONL 文件形式,存储在项目专属路径下(显式的清理重写除外)(图 8)。getTranscriptPath() 函数(sessionStorage.ts)将其计算为 join(projectDir, ${getSessionId()}.jsonl),其中 projectDir 通过先检查 getSessionProjectDir()(在恢复/分支期间由 switchSession() 设置),再回退到 getProjectDir(getOriginalCwd())() 来确定。

三个持久化通道独立运作:

1. **会话转录:** 包括用户、助手、附件和系统消息在内的对话记录,外加压缩及其他元数据事件。限定于项目范围,每个会话一个文件。
2. **全局提示词历史:** 仅包含用户提示词,存储在 Claude 配置主目录下的 history.jsonl 中(history.ts)。makeHistoryReader() 生成器通过 readLinesReverse() 以倒序产出条目,支持向上箭头和 ctrl+r 导航。
3. **子智能体侧链:** 每个子智能体各有单独的 .jsonl + .meta.json 文件(第 8.3 节)。

会话转录存储了除简单消息之外的多种事件,包括压缩标记、文件历史快照、归属(attribution)快照和内容替换记录。仅追加的 JSONL 格式是一个有意的选择,偏向可审计性和简单性,而不是查询能力。每个被记录的事件都是人类可读的、可版本控制的,并且无需专门工具即可检查。基于数据库的替代方案可以对会话历史进行更丰富的查询,但会引入部署依赖并降低透明度。

会话身份系统将 sessionId 与 sessionProjectDir 配对,二者在恢复或分支期间一起设置。转录路径必须使用写入消息时处于活动状态的同一个项目目录,以避免 hooks 在错误的目录中查找。

### 9.2 恢复、分叉与不还原权限

--resume 标志通过重放转录来重建对话(conversationRecovery.ts)。分叉(Fork)则从一个已有会话创建新会话(commands/branch/branch.ts)。然而,恢复和分叉不会还原会话范围的权限;用户必须在新会话中重新授予。这是一个出于安全保守考虑的有意设计:会话被视为相互隔离的信任域。在恢复时还原先前授予的权限,会带来便利,但有把过时的信任决定带入已变化的上下文的风险。该架构选择重新授予而非隐式持久化,接受用户摩擦作为代价,以维持"信任总是在当前会话中建立"这一安全不变量。

compact_boundary 标记经过精心设计,以配合持久化。annotateBoundaryWithPreservedSegment() 函数(compact.ts)在边界事件中记录 headUuid、anchorUuid 和 tailUuid。这些 UUID 使会话加载器能够在读取时修补消息链:被保留的消息在磁盘上保持其原始的 parentUuid,加载器利用边界元数据把它们正确地链接起来。这种以追加为主的设计意味着压缩通常不会修改或删除先前写入的转录行。

Claude Code 中的"检查点"是用于 --rewind-files 的文件历史检查点,存储在 ~/.claude/file-history/<sessionId>/ 下。这些是用于还原文件系统更改的文件级快照,而不是通用的检查点存储。

## 10 对比分析:Claude Code、OpenClaw 与 Hermes Agent

前面各节记录了 Claude Code 对循环架构、安全、扩展性、上下文管理、委派和持久化等反复出现的设计问题的回答。为了把这些发现置于更广阔的智能体设计空间之中,本节将 Claude Code 与两个独立的开源 AI 智能体系统进行比较,它们从根本不同的出发点回答许多相同的设计问题。

OpenClaw 是一个本地优先的 WebSocket 网关,将消息界面(WhatsApp、Telegram、Slack、Discord、Signal 等)连接到一个嵌入式的智能体运行时,并配有 macOS、iOS 和 Android 上的配套应用(Steinberger and OpenClaw Contributors, 2026)。Hermes Agent 是单一的 Python 进程,其角色由调用它时所用的入口点决定,一个持久化层、多个界面共同面向同一个运行时(Nous Research, 2026)。⁴ Hermes 发行版暴露三个控制台脚本:hermes 用于 CLI 和网关控制器,hermes-agent 用于批量运行,hermes-acp 用于 Agent Client Protocol 适配器,让外部 IDE 能够托管 Hermes,就像 Hermes 自己的网关可以托管其他智能体那样。Claude Code 是绑定于单个仓库会话的 CLI 编程 harness,OpenClaw 是面向多渠道个人协助的持久控制平面,而 Hermes 是一个进程,其角色和界面集合由启动它的入口点决定。这三个系统占据智能体设计空间的不同区域。这一比较的价值在于展示:当部署环境改变时,同样反复出现的问题如何产生不同的架构答案。

> ⁴ 对 Hermes 的基于源码的阅读发现了两处项目自身文档与实现不一致的情况:SECURITY.md 记载的批准模式分类是 on/auto/off,而 tools/approval.py:721-750 返回的是 manual/smart/off;SECURITY.md 和 AGENTS.md 都描述委派深度默认为二,而 tools/delegate_tool.py:128 设置的是 MAX_DEPTH = 1。我们引用的是源码而非文档。

三者之间还存在组合关系:OpenClaw 可以通过其 ACP(Agent Client Protocol)集成,将 Claude Code、OpenAI Codex 和 Gemini CLI 作为外部编程 harness 托管;而 Hermes Agent 同时位于 ACP 主机/客户端划分的两侧,其网关托管平台适配器和工具服务器,同时其 hermes-acp 适配器让外部 IDE 托管 Hermes,使这些系统可以叠加,而不是纯粹的替代关系。

**系统范围与部署模型。** Claude Code 作为绑定于单个仓库的临时 CLI 进程运行。每个会话随终端开始和结束。OpenClaw 作为持久的守护进程运行(默认端口 18789,仅回环),拥有所有消息界面连接,并通过带类型的 WebSocket 协议协调客户端、工具和设备节点。Hermes Agent 作为单个长期存活的 Python 进程运行,其角色由启动它所用的入口点固定;其网关子命令通过两层适配器系统驱动消息界面(gateway/platforms/ 下的树内适配器,外加 plugins/platforms/ 下用于 Google Chat、IRC 和 Teams 的插件层),并把会话和多智能体看板状态持久化到两个磁盘上的 SQLite 文件(state.db 和 kanban.db),而不是通过带类型的 WebSocket 协议。这使 Hermes 在信任拓扑上更接近 OpenClaw 而非 Claude Code,但在进程拓扑上更接近 Claude Code 而非 OpenClaw;"代理(broker)放在哪里"这一设计问题,在 Hermes 中的答案是根本没有代理。这些系统范围上的差异是比较中最根本的架构分歧:它们决定了其他所有设计问题如何被提出。

**信任模型与安全架构。** 三个系统应对不同的威胁模型。Claude Code 假设在受信任开发者的机器上运行着一个不受信任的模型:默认拒绝的权限系统(第 5 节)评估每一次工具调用,ML 分类器提供自动化的安全评估,七种权限模式构成渐进的自主性谱系。OpenClaw 假设每个网关实例只有一个受信任的运营者。其安全架构从身份与访问控制(私信配对码、发送者允许列表、网关认证)开始,而不是逐操作的安全分类。工具策略使用按智能体配置的允许/拒绝列表,而不是集中式的分类器。沙箱作为可选择启用的功能提供,有多种后端(Docker、SSH 或 OpenShell)和可配置的范围(每智能体、每会话或共享);启用时,非主(non-main)模式可以将所有非主会话沙箱化,但沙箱默认并不启用。OpenClaw 的安全文档明确声明,共享网关上的敌对多租户隔离不是受支持的安全边界。Hermes Agent 采取第三种立场。工具授权集中在一个文件中(tools/approval.py),暴露三种模式(manual、smart、off)和一个无条件的 HARDLINE_PATTERNS 底线,无论哪种模式都会阻止 rm -rf /、mkfs、对块设备的原始 dd、fork 炸弹和系统关机命令(B 级证据)。smart 模式运行一个辅助 LLM 的风险评估;源码中的一条注释点明 OpenAI Codex 的智能批准(smart approvals)是其设计灵感来源。由于 Hermes 运行于众多界面之上,同一套批准流程被呈现四次:CLI 提示、Telegram、Discord 和 QQBot 上的网关批准键盘、面向 IDE 客户端的 ACP request_permission 往返,以及用于无人值守运行的仅限 cron 的模式。与 Claude Code 的七模式分类和由 ML 分类器驱动的自动模式相比,Hermes 的模式分类更小,但具有相同的多层结构:无条件的安全底线、默认的交互式提示、可选择启用的辅助 LLM"smart"路径。架构上的答案相同;不同的是界面数量。三者之间的差异反映了信任边界所在的位置:Claude Code 把它放在模型与执行环境之间,OpenClaw 把它放在网关边界上,而 Hermes 居于两者之间,像 Claude Code 一样进行逐操作批准,却像 OpenClaw 一样通过许多界面呈现。

**智能体运行时与工具编排。** 三个系统都实现了智能体循环,但这些循环在各自架构中的位置不同。在 Claude Code 中,queryLoop() 异步生成器(第 4 节)是系统的中心:所有界面都汇入其中,它直接管理上下文组装、模型调用、工具分派和恢复。在 OpenClaw 中,智能体运行时是一个嵌入式的 pi-coding-agent 核心(OpenClaw 所集成的、来自 pi-mono 项目的外部 SDK),位于更大的网关分派层之内。网关的智能体 RPC 校验参数、解析会话并立即返回;嵌入的运行器随后执行智能体循环,同时通过网关协议向外发出生命周期和流事件。运行通过每个会话的队列和一个可选的全局通道进行串行化,防止跨多渠道界面的工具和会话竞争。在 Hermes Agent 中,循环是 AIAgent.run_conversation(run_agent.py)内部的一个同步 while,受迭代次数(默认 90)和一个单独的迭代预算限制;当预算耗尽时,一次去除工具的摘要调用让智能体给出一条收尾消息,而不是中途终止(B 级证据);每次迭代发送由 model_tools.get_tool_definitions() 收集的工具模式,并通过 model_tools.handle_function_call 路由任何工具调用,tools/*.py 中的工具文件在导入时自注册,因此添加一个工具只需要一次 registry.register() 调用,而一条助手消息中返回的多个工具调用会被并行执行,并带有顺序回退。三个系统都遵循 ReAct 模式(Yao et al., 2022),其中 OpenClaw 的循环是控制平面中的一个组件,而不是控制平面本身;Hermes 的循环在运行时层面与 Claude Code 的循环是对等的,但实现形态不同:是由线程管理并发的同步 Python 循环,而不是产出(yield)的异步生成器。

**扩展架构。** Claude Code 的四种扩展机制(MCP、插件、skills、hooks)按上下文成本组织(第 6 节):hooks 消耗零上下文,skills 消耗低上下文,MCP 服务器消耗高上下文。四者都是扩展单个智能体的上下文窗口和工具面。OpenClaw 使用清单优先的插件系统,有四个架构层(发现、启用、运行时加载、界面消费)和十二种能力类型,包括文本推理、语音、媒体理解、图像/音乐/视频生成、网页搜索和消息渠道。插件把能力注册到中央注册表中;网关读取注册表,以暴露工具、渠道、提供者设置、hooks、HTTP 路由、CLI 命令和服务。OpenClaw 还有一个独立的 skills 层,有多个来源(工作区、项目级、个人、受管、内置和额外目录,其中工作区 skills 优先级最高),外加一个公共注册表(ClawHub),并通过内置的 openclaw mcp 命令支持 MCP(服务器和出站客户端注册表)。Hermes Agent 暴露五个扩展界面,而 Claude Code 为四个(B 级证据):其中三个与 Claude Code 处于同一层级(plugins/<name>/ 下带生命周期 hooks 的通用插件、skills/ 下的内置 skills,以及 config.yaml 中配置的 MCP 服务器),另外两个额外的界面沿着不同的轴扩展(plugins/memory/<name>/ 下的可插拔记忆提供者,以及 plugins/model-providers/<name>/ 下的可插拔模型提供者),让 Hermes 可以替换后端,而不是拦截事件。Hermes 中的 hooks 可以是进程内的 Python 回调,也可以是由配置驱动的外部 shell 命令,二者都通过同一个 hook 管理器分派。当 Hermes 派生一个 stdio MCP 服务器时,子进程的环境在启动前被限制在一个小的系统变量允许列表内,并且 npx/uvx 包名会对照 OSV 恶意软件数据库进行筛查。三者之间的架构差异在于扩展作用的位置:Claude Code 的扩展修改单个智能体的动作面,OpenClaw 的插件扩展跨所有智能体的网关能力面,而 Hermes 的扩展则在 Claude Code 风格的每智能体界面之上增加了第二条轴,原地替换整个记忆和模型提供者后端,而不是在其周围拦截事件。

**记忆、上下文与知识管理。** 三个系统都使用透明的基于文件的记忆,而不是不透明的数据库。Claude Code 加载四级 CLAUDE.md 层级,并通过五层压缩流水线管理上下文压力(第 7 节)。记忆检索使用基于 LLM 的文件头部扫描。OpenClaw 在会话开始时把工作区引导文件注入系统提示词:五个核心文件(AGENTS.md、SOUL.md、TOOLS.md、IDENTITY.md、USER.md),外加有条件的 BOOTSTRAP.md、HEARTBEAT.md 和 MEMORY.md,较大的文件会被截断。另外,记忆系统管理三种文件类型:用于长期持久事实的 MEMORY.md、带日期戳的每日笔记(memory/YYYY-MM-DD.md),以及用于"做梦"清扫摘要的可选 DREAMS.md。当配置了嵌入提供者时,记忆搜索使用把向量相似度与关键词匹配相结合的混合检索。一个实验性的"做梦"系统执行后台整合,对候选项打分,并只把合格的条目从短期回忆提升到长期记忆。在压缩之前,OpenClaw 会自动提醒智能体把重要笔记保存到记忆文件中,以防上下文丢失。Hermes 中的压缩是一个辅助 LLM 摘要器,带 token 预算的尾部保护,并且之前有一道工具输出修剪环节;摘要以一段很长的"仅供参考"前言开头,告诉智能体压缩内容是背景上下文而不是新指令,并且持久记忆(MEMORY.md、USER.md)仍具权威性(B 级证据)。Claude Code 的 CLAUDE.md 层级是固定的,压缩有五层,而 Hermes 的压缩层数更少,但增加了上下文文件的预注入扫描:AGENTS.md、.cursorrules 和 SOUL.md 之类的文件会对照一份注入模式和不可见 Unicode 字符的列表进行检查,任何命中都会把该文件的内容替换为一个 [BLOCKED: ...] 标记。三者共同承诺用户可见、可编辑的记忆,但对同一个上下文管理问题给出不同的答案:Claude Code 投入于分级的上下文压缩(五层,具备缓存感知);OpenClaw 投入于结构化的长期记忆晋升(做梦、每日笔记、记忆搜索),外加可插拔的压缩提供者和会话修剪,不过其压缩流水线不如 Claude Code 的五层系统那样分级;Hermes 则投入于预注入内容扫描,以及在提示词层面把持久记忆与压缩后的历史相隔离,而不是更深的压缩堆栈。

**多智能体架构与路由。** 这一维度揭示了最鲜明的架构差异。Claude Code 的多智能体模型是任务委派:父级派生子智能体(Explore、Plan、通用和自定义类型),它们在隔离的上下文窗口中运行,工具集受限,并仅返回摘要结果(第 8 节)。工作树隔离提供文件系统级别的分离。OpenClaw 区分两个不同的关注点。第一,多智能体路由:单个网关可以托管多个完全隔离的智能体,每个都有自己的工作区、认证配置、会话存储和模型配置,并通过确定性的绑定规则被路由到特定渠道或发送者。第二,子智能体委派:在单个智能体内部,可以派生后台运行,其嵌套深度可配置(最大 5,默认 1,推荐 2),在受支持的渠道上有线程绑定会话,并按深度配置工具策略。OpenClaw 的项目愿景明确拒绝把智能体层级框架作为默认架构。Hermes Agent 则沿着又一条不同的接缝来划分这个问题。每回合的委派通过 delegate_task 工具进行,它在线程池中派生子 AIAgent 实例;父级会阻塞直到子级返回摘要,并发默认限制为三个子智能体,深度上限为一(限制在 [1, 3] 范围内),叶子子智能体默认不能自己再委派(嵌套委派通过编排者子智能体和更高的派生深度设置来选择启用),并且子智能体始终在持久记忆被禁用的情况下运行,因此无法读写父级的笔记(B 级证据)。除了每回合委派之外,v0.13 的 Kanban 子系统是一个基于 SQLite 的工作队列,多个 Hermes 工作者配置在其中认领、发送心跳并完成任务,带有过期认领的回收,并在连续两次失败尝试后自动阻塞(hermes_cli/kanban_db.py:2703)。这三者之间的区别很重要,因为:Claude Code 的子智能体是单个用户编程会话内的从属工作者;OpenClaw 的多智能体路由创建真正独立的智能体实例,通过不同渠道服务不同的用户或目的;而 Hermes 把严格的每回合委派默认设置与一个单独的 Kanban 层结合起来,让多个智能体进程通过一块持久的共享看板进行协调,这是 Claude Code 和 OpenClaw 没有以同样形式提出的问题。

### 10.2 Hermes Agent:对比表之外的能力

Hermes 中的会话持久化使用一个 WAL 模式的 SQLite 数据库,支持对所有会话消息的全文搜索,以及一条记录由压缩触发的拆分的父会话链(B 级证据)。Claude Code 把会话持久化为每个项目的 JSONL 文件(第 9 节),而 Hermes 的选择开箱即用地提供跨会话搜索和并发读取支持。当网关在对话中途重启时,会话会在下一条消息到达时自动恢复,由基于转录时间戳新鲜度的逻辑驱动,默认窗口为一小时。内置的 cron 调度器和 webhook 订阅系统让智能体可以按调度表达式或外部 HTTP 事件无人值守运行;cron 会话在持久记忆被禁用的情况下运行,并带有默认为 600 秒的可配置不活动超时。该发行版还包含一个后台的"策展人(curator)"循环,用于审查智能体创建的 skills、归档陈旧的 skills,并且从不删除,仅限于具有智能体来源的 skills,因此内置和从 hub 安装的 skills 不在其范围内。这些能力都无法清晰地映射到主表所用的六个比较维度上,这就是它们在这里作为 Hermes 特有的补充出现,而不是作为表 3 中的单元格。OpenClaw 的独特能力(扩展架构下的 ClawHub 插件注册表和记忆与上下文下的"做梦"记忆子系统)已经占据了这六个维度中的单元格,因此不需要并行的补充。本小节中 Hermes 的补充内容源于其持久进程的范围,这是 Hermes 与 OpenClaw 共有的部署环境属性,但 Claude Code 的每会话 CLI 模型并不具备。

### 10.3 对比揭示了什么

这一比较展现了关于 AI 智能体系统设计空间的三点观察。

第一,3.1 节中识别出的反复出现的设计问题(推理位于何处、采取何种安全姿态、如何管理上下文、如何构造扩展性)的适用范围超出了编程智能体。OpenClaw 从多渠道个人助理而不是绑定仓库的编程工具的出发点回答这些问题中的每一个,而 Hermes Agent 则从单进程、多界面的部署而不是 CLI harness 或多渠道网关来回答它们。问题是稳定的;答案则随三个系统的部署环境而变化。

第二,这些系统在若干维度上下了不同的赌注。Claude Code 投入于分级的逐操作安全评估;OpenClaw 投入于边界级的身份与访问控制;Hermes 居于两者之间,像 Claude Code 一样做逐操作批准,却像 OpenClaw 一样通过许多界面来呈现。Claude Code 把智能体循环视为架构中心;OpenClaw 把网关控制平面视为中心,并把智能体循环作为一个组件嵌入;Hermes 的循环在运行时层面与 Claude Code 的循环是对等的,占据同样的架构位置,而不是位于网关分派层之内。Claude Code 的扩展修改单个上下文窗口;OpenClaw 的插件扩展共享的网关界面;Hermes 在 Claude Code 风格的每智能体界面之上增加第二条轴,原地替换记忆和模型后端,而不是拦截事件。这些差异并非任意的:它们源于三个系统不同的信任模型和部署拓扑。

第三,三个系统之间的组合关系在架构上意义重大。OpenClaw 可以通过 ACP 把 Claude Code 作为外部编程 harness 托管,而 Hermes Agent 位于主机/客户端划分的两侧:其网关托管平台适配器和工具服务器,其 hermes-acp 适配器则让外部 IDE 托管 Hermes。这些系统是可组合的,而不是相互排斥的替代品,这表明 AI 智能体的设计空间并不是一个扁平的分类,而是一个分层的结构,网关级系统和任务级 harness 可以在多个位置组合。

## 11 相关工作

### 11.1 编程智能体分类

AI 编程工具可以按其支持的自主行动程度来组织(表 4)。GitHub Copilot(Chen et al., 2021)等行内补全工具在编辑器内建议代码片段,不进行自主行动。Cursor 和 Windsurf 等聊天集成型产品增加了对话式交互和多文件编辑,但仍与 IDE 环境耦合。智能体式 CLI 工具,包括 Claude Code、OpenAI 的 Codex CLI 和 Aider(Gauthier, 2024),从命令行运行,可以在单个请求内自主执行 shell 命令、读写文件并对输出进行迭代。Devin、SWE-Agent(Yang et al., 2024)和 OpenHands(Wang et al., 2024b)等完全自主系统追求最少的人类监督,通常运行在沙箱化的云环境中。

**表 4** 按自主行动程度划分的 AI 编程工具类别。

| 类别 | 示例 | 模式 |
|---|---|---|
| 行内补全 | Copilot、Tabnine | 编辑器插件 |
| 聊天集成 | Cursor、Windsurf、Cody | 与 IDE 耦合的产品 |
| 智能体式 CLI | Claude Code、Codex CLI、Aider | 工具调用循环 |
| 完全自主 | Devin、SWE-Agent、OpenHands | 沙箱 + 规划 |

Claude Code 与更高自主性的智能体共享一些特性(自动模式分类器、后台智能体执行、远程环境),但默认保留交互式批准。SWE-Bench(Jimenez et al., 2023)和 HumanEval(Chen et al., 2021)等评测基准推动了学术界对编程智能体的大部分关注。本文则从源代码出发考察 Claude Code 的内部架构。

### 11.2 智能体架构模式

Claude Code 的核心循环遵循 ReAct 模式(Yao et al., 2022):模型生成推理和工具调用,harness 执行动作,结果被送入下一次迭代。Toolformer(Schick et al., 2023)证明了语言模型可以学会使用工具。Claude Code 使用最多 54 个内置工具和分层的权限系统。更广阔的设计空间已被若干综述所描绘。Weng(2023)提出了如今已成标准的"规划、记忆与工具使用"分解,Wang et al.(2024a)梳理了早期的自主智能体工作。Xu(2026)围绕三个反复出现的权衡来构建该领域的框架(自主性与可控性、延迟与准确性、能力与可靠性),这些权衡在我们的分析中反复出现;Hu et al.(2024)则把智能体设计本身视为对组件、算法和评估函数的搜索问题。本文刻画的是该空间中的一个具体点。

一篇关于"代码作为智能体 harness"的近期综述,把代码不仅视为模型输出,更视为推理、行动、环境建模和基于执行的验证的基底(Ning et al., 2026)。这一框架与本文关注模型周围的 harness,而不仅仅是基准分数的重点相吻合。

AutoGen(Wu et al., 2024)、LangChain 和 CrewAI 等多智能体编排框架提供基于对话的智能体协调。Claude Code 的子智能体委派(第 8 节)包括权限覆盖的优先级、两级权限作用域,以及每个子智能体独立的转录文件。LATS(Zhou et al., 2023)在树搜索框架中统一了推理、行动和规划。Claude Code 的 plan 权限模式则实现了一种更简单的"先规划后执行"方法。

从业者的写作已经汇聚到若干反复出现的模式,Claude Code 的架构正是它们的实例。Anthropic 自己的《构建有效的智能体》(Schluntz and Zhang, 2024)区分了智能体与工作流,并主张采用简单、可组合的模式,而不是笨重的框架。Martin(2026)综合了在生产系统中观察到的七种模式,包括赋予智能体文件系统和 shell 访问权限作为通用的动作层,以及按需发现动作,而不是预先加载所有工具模式。Chase(2025)观察到 Claude Code 的规划工具"基本上是个空操作(no-op)",其价值在于让智能体保持在正轨上,而不是执行任何外部计算。Wang(2025)认为,授权(authority)是学术框架最常遗漏的要素,称信任是生产级智能体设计中"最被忽视的要素",而第 5 节的权限分析试图弥补这一缺口。Huyen(2025)使复合误差问题变得具体:在每步准确率为 95% 的情况下,一个 100 步的任务只有 0.6% 的概率成功,这促使了我们在第 4 节和第 5 节中追踪的逐步验证模式。OpenAI 在其关于 harness 工程的文章中也提出类似观点,把 harness 本身的设计视为一项核心工程任务(OpenAI, 2026a)。近来还出现了一个名为"循环工程(loop engineering)"的新概念:开发者不再在每个回合向智能体发出提示,而是构建一个循环,用以发现工作、分配工作、检查结果并决定下一步,它由本文记录的同样的原语组装而成,例如 skills、MCP 服务器和子智能体(Osmani, 2026)。它使单个开发者能够自主指挥远多得多的工作,并已引起关注,包括来自 Claude Code 自己团队的关注,不过,减少人在每个回合中的参与,也使第 14 节将再次回到的"开发者长期能力"问题更加尖锐。

**上下文管理。** 表 5 给出了上下文管理方法的设计空间分类。Claude Code 的五层压缩流水线在升级之前,会在不同粒度上应用多种策略,并具有感知缓存的压缩和读时虚拟视图语义。Zhang et al.(2025a)刻画了这一设计所缓解的两种失效模式(摘要丢失领域细节,以及迭代式上下文重写导致的细节丢失),并转而建议把上下文视为一本随时间累积策略的"演化中的手册(evolving playbook)"。Claude Code 的做法与这一框架一致,因为 CLAUDE.md 层级累积的是结构化的指令,而不是反复对它们进行摘要。Hu et al.(2025)区分了上下文工程与智能体记忆:上下文工程处理瞬时的组装,而记忆涵盖持久的事实性知识和经验痕迹。Claude Code 的架构以同样的方式将二者分开,把压缩流水线与基于文件的记忆层级配对。

**表 5** 基于 LLM 的工具中上下文管理方法的设计空间。

| 方法 | 机制 | 粒度 |
|---|---|---|
| 简单截断 | 丢弃最旧的消息 | 粗 |
| 滑动窗口 | 固定大小的近期历史 | 中 |
| RAG | 检索相关片段 | 细 |
| 单次摘要 | 一遍压缩 | 粗 |
| 分级压缩 | 多层流水线 | 非常细 |

**安全与权限。** 生产级编程智能体采用的安全架构沿三个轴变化:批准模型(逐操作提示、分类器介导的自动化,或不提示但事后审查)、隔离边界(操作系统级容器、文件系统沙箱、受权限限定的工具池,或无)和恢复机制(版本控制回滚、会话范围的权限重置,或基于检查点的回退)。SWE-Agent 和 OpenHands(Yang et al., 2024;Wang et al., 2024b)主要依赖 Docker 容器隔离,提供约束所有智能体动作的环境级沙箱。Codex CLI 支持针对 shell 命令的沙箱模式和批准策略。Aider(Gauthier, 2024)使用 Git 作为其主要安全机制,使所有更改都可以通过版本控制回退。Claude Code 把逐操作的默认拒绝规则、用于自动批准的基于 ML 的分类器、可选的 shell 沙箱,以及会话范围权限的不还原结合起来,分层叠加多种机制,而不是依赖单一的隔离边界。

沙箱相关的报告使这一边界变得具体。OpenAI 关于其 Windows 沙箱的讨论描述了:写入权限限定在工作目录和已配置的可写根目录内,并对这些根目录中选定的只读路径设置显式拒绝规则(OpenAI, 2026b)。Cursor 的云智能体报告则补充了同一问题的云端一侧:网络策略、密钥脱敏和凭据管理成为智能体环境的一部分(Ma, 2026)。这些细节使安全边界成为一个执行边界,而不仅仅是一个批准提示。

**协议与扩展性。** Claude Code 用作主要外部工具集成的模型上下文协议(MCP),已成为一个事实标准,拥有庞大的生态系统,也带来相应的攻击面。Hou et al.(2025)梳理了 26 个主要目录中数千个社区开发的 MCP 服务器,并把 MCP 特有的威胁归纳为四类攻击者和十六种场景,包括工具投毒(tool poisoning)、抽地毯(rug pulls)和跨服务器遮蔽(cross-server shadowing)。第 5 节中分析的权限和拒绝规则机制,以及第 6.2 节中的预过滤步骤,可以被理解为该综述所呼吁的缓解措施的运行时一侧。同样的观点也适用于更高层的工具设计。美国国家安全局(NSA)的指南把 MCP 安全视为一个贯穿协议设计、运行时调度、与外部服务集成以及长期监控的生命周期问题(National Security Agency, 2026)。一项面向智能体优先的工具设计的提案认为,面向智能体的 API 应提供搜索、解析、预览、执行、验证和恢复等阶段,而不仅仅是面向人类的 CRUD 端点(Pan, 2026)。从这个角度看,MCP 服务器、插件、skills、SDK 和智能体间协议构成了一条工具供应链:它们扩展了智能体能做的事情,但也需要身份、允许列表、版本管理、审计日志和撤销机制。

**软件架构。** 分层架构模式(Garlan et al., 1993)为我们的五层分解提供了参考。基于角色的访问控制模型(Sandhu et al., 2002)为权限模式系统提供了理论依据。浏览器沙箱(Reis and Gribble, 2009)是一种类似的按进程隔离的方法。多智能体系统理论(Wooldridge, 2009)有助于解释子智能体委派。

**定位。** 此前关于编程智能体的工作集中于基准(智能体解决任务的能力如何)、框架(如何组合智能体)和产品(用户能做什么)。本文贡献的是对一个生产级编程智能体的、以源码为依据的设计空间分析,利用源码级分析和架构对比来揭示设计选择与权衡。它借鉴了软件架构案例研究的传统(Garlan et al., 1993),但通过系统地识别设计问题、映射备选方案,并将 Claude Code 的选择与 OpenClaw 和 Hermes Agent 这两个在不同部署场景下运作的独立 AI 智能体系统进行对比,把它应用于基于 LLM 的智能体。

## 12 讨论

前面各节记录了 Claude Code 如何回答关于循环架构、安全姿态、扩展性、上下文管理、委派和持久化的反复出现的设计问题。每个答案都反映了设计空间中的一个位置,既有真实的备选方案,也有可衡量的权衡。本节考察把这些答案放在一起阅读时所揭示的内容:它们所反映的设计理念(第 12.1 节)、它们所造成的价值张力(第 12.2 节)、它们所带来的架构权衡(第 12.3 节)、它们所产生的实证预测(第 12.4 节),以及跨子系统反复出现的贯穿性承诺(第 12.7 节)。本节按照第 2.1 节的五价值框架来组织。

### 12.1 设计理念

第 2 节介绍的价值和设计原则预测了这样一种架构:它投入于运行基础设施,而不是决策脚手架。实现证实了这一点:第 3 至 9 节记录的架构绝大部分是确定性的基础设施(权限闸门、工具路由、上下文管理、恢复逻辑),而 LLM 只是被当作一个无状态的补全端点来调用。估计有 1.6% 的代码库属于决策逻辑,其余 98.4% 是运行 harness。这个比例并非偶然。

第 2.2 节中记录的设计原则支撑了这种做法:harness 创造让模型能够做出良好决策的条件,而不是约束它的选择。

这种设计与智能体工程中的主流模式背道而驰:LangGraph 等框架通过带类型边的显式图节点来路由模型输出,Devin 等系统则把多步规划器与笨重的运行基础设施搭配在一起。Claude Code 则是在丰富的运行 harness 之内给予模型最大的决策空间。其工程复杂性的存在并非为了约束模型的决策,而是为了成就这些决策。这种由模型推理、由 harness 强制执行的分层架构,引出了一个问题:智能体式编程工具是否正在向类似操作系统的抽象收敛,其中核心循环充当内核,其余一切构成操作系统。

随着前沿模型在编程任务上的实际能力趋同,这一设计具有了额外的意义:周边运行 harness 的质量成为主要的差异化因素,这验证了一种投入于基础设施而非决策脚手架的架构。对智能体构建者而言,其含义是:投入于上下文管理、安全分层和恢复机制等确定性基础设施,可能比围绕日益强大的模型添加规划脚手架带来更大的可靠性收益。近期的原生运行时基准测试为这一原本基于推理的论断提供了直接的实证支持:固定模型、只改变周边的 harness,就能使单个模型在长时程任务上的得分变化最多达 18 分,所测试的 harness 包括 Claude Code 和 OpenClaw(Ding et al., 2026)。

**(C 级证据)** 随着模型能力变强,对于像 Fable 5 这样能自行阅读代码库并修复问题的模型,harness 是否仍然必要?harness 服务于第 2.1 节的五项价值,其中只有一项,即能力放大,主要与模型的能力强弱有关。在这一项之内,更强模型所影响的部分是决策脚手架,也就是某些框架包裹在模型外面、引导并约束它走向解决方案的规划和控制逻辑。在模型已经很强的地方,例如代码和数学领域,它自己就能得到成功的解答,因此这种引导和约束就不那么必要了。另外四项价值主要与模型能力强弱无关,因此服务于它们的 harness 依然保留。可靠执行是部分的例外:更强的模型能更准确地理解请求,也能稍好地修正自己的错误。但是上下文窗口仍然是有限的,会话仍然需要恢复,而且模型每次运行仍倾向于以不同的方式重建同样的东西,因此上下文管理与恢复仍然需要。安全、保障与隐私完全不依赖于能力。默认拒绝规则、沙箱、自动模式分类器和审计日志与以往同样重要,而更强的模型风险更大而不是更小:Fable 5 本身在较高风险的领域就被安全分类器所限制(Anthropic, 2026c)。人类决策权关乎人的决定权,而不是模型的能力,因此批准、中断和转录保持其作用。情境适应性与之类似:强模型仍然是一个没有见过你的代码的通用模型,因此 CLAUDE.md、skills 和 MCP 仍然使它适配你的项目。约束全部五项的 token 经济学同样没有放松,因为更好的模型并不会让 token 变得免费。

研究表明,即使对最强的模型也是如此:仅仅改变 harness 的选择,就能使 Fable 5 的功能性和安全性通过率变化十个百分点或更多(Compagna, 2026)。随着模型能力增长,harness 并不会变得无用;变化的只是决策脚手架,而且只发生在模型已经很强的地方,而它所做的其他一切依然像以前一样重要。

综上,前面各节表明,生产级编程智能体面临反复出现的设计选择:推理相对于 harness 位于何处、迭代循环如何构造、默认采取何种安全姿态、扩展面如何划分、上下文如何组装和压缩、子智能体如何委派与编排,以及会话如何跨越边界持久化。Claude Code 对这些问题的回答构成了一个连贯的设计点,即在丰富的运行 harness 之内,优先保障模型的自主性。这一理念假设,丰富的确定性基础设施足以支撑不受约束的模型判断。以下各小节考察这一假设在何处受到检验。

### 12.2 价值张力

第 2.1 节中识别出的五项价值会产生张力,即追求其中一项价值会约束另一项(表 6)。这些张力并非设计失败;它们是同时追求多项价值的结构性后果。我们报告的是证据最有力的张力,而不是完整的组合集合。

另一个独立的问题是,短期收益是否会削弱开发者的长期能力(第 2.4 节)。一项涉及 16 名经验丰富的开发者、246 个任务的随机对照试验(Becker et al., 2025)发现,AI 工具使开发者慢了 19%,尽管他们主观感觉提升了 20%。一项对 807 个仓库中 Cursor 采用情况的因果分析(He et al., 2025)发现,代码复杂度增加了 40.7%。一项涉及 54 名参与者的脑电图(EEG)研究(Kosmyna et al., 2025)发现,LLM 使用者表现出神经连接减弱,并且在移除 AI 之后仍然持续。研究者已经提出了用于衡量 AI 辅助编程中认知卸载的协议,其动机是担忧使用 AI 的学生做出了应用,却不理解其底层逻辑(Aiersilan, 2026)。这些发现,再加上 2023 至 2024 年间入门级技术岗位招聘下降了 25%(Rak, 2025),表明能力放大与长期可持续性之间的张力,已超出个人生产力的范围,延伸到更广泛的开发者人才梯队。这些证据推动了长期能力问题,但并非专门针对 Claude Code 的架构。它与那些依赖有限上下文、工具调用循环和局部生成决策的智能体系统最为相关。

**表 6** 价值之间的张力及其支持证据。每一种张力都表明,这两项价值所涉及的确实是不同的关切。

| 价值对 | 张力 | 证据 |

### 12.3 架构权衡

表 6 中的张力在四个方面体现为具体的架构权衡。上文记录的长期可持续性担忧,将在第 12.4 节的实证预测中浮现。

**安全 vs. 自主性。** 权限模式(五种始终存在,外加分类器功能开关启用时的 auto 以及内部的 bubble 模式)形成了一个梯度:从 plan(用户批准所有计划),经过 default、acceptEdits、auto(ML 分类器),直到 bypassPermissions(跳过大多数提示,但安全关键的检查仍然保留)。这一递进代表着随着自主性增加而单调递减的安全梯度。恢复时不还原权限,反映了一种偏向安全的有意选择:安全状态不会隐式地跨越会话边界而持续存在。

安全—自主性梯度不仅由架构设计塑造,也由用户行为塑造。Anthropic 的自动模式分析(Hughes, 2026)发现,用户批准约 93% 的权限提示,表明审批疲劳使交互式确认在行为上不可靠。纵向使用数据(McCain et al., 2026)显示,自动批准率从不足 50 个会话时的约 20%,上升到 750 个会话时的 40% 以上,同时会话时长大幅增加。这些模式表明,这个梯度不是通过有意的模式选择来穿越的,而是通过逐渐的习惯化。沙箱使权限提示的频率估计降低了 84%(Dworken and Weller-Davies, 2025),把问题重新框定为一个人因(human-factors)问题:面对不可靠的人类批准,架构上的应对是减少人类必须做出的决定的数量。

更根本的是,第 5 节所述的纵深防御架构建立在一个独立性假设之上:如果一个安全层失效,其他层会捕获违规。但 Claude Code 的各安全层共享共同的性能和经济约束。自动模式分类器是一次单独的 LLM 调用,有直接的 token 成本。bashSecurity.ts 模块执行基于 AST 的顺序检查,带有解析延迟。默认拒绝的规则评估作用于命令结构。当性能压力推动降低这些成本时,各层可能同时退化。安全研究人员(Adversa.ai, 2026)记录到,超过 50 个子命令的命令会回退到单一的通用批准提示,而不是运行逐子命令的拒绝规则检查,因为逐子命令的解析曾导致 UI 卡顿,这表明当独立性假设被违反时,纵深防御会失效。

这种张力是结构性的。任何使用模型本身进行安全评估的、基于 LLM 的智能体系统都会面临它。相关的评估标准不是任何单个层是否可以被绕过,而是有多少个独立的层必须同时失效,以及它们是否共享失效模式。

**对抗条件下的权限模型。** 独立的安全研究为权限架构提供了实证验证,具体而言,是揭示了图 4 中没有捕捉到的一个时序性质。两个经独立验证的漏洞共享一个根本原因:信任之前的初始化顺序(pre-trust initialization ordering):在项目初始化期间执行的代码(hooks、MCP 服务器连接和设置文件解析),会在向用户展示交互式信任对话框之前就运行了。⁵ 这个信任前的执行窗口落在默认拒绝评估流水线(permissions.ts)之外,形成了一个结构上享有特权的阶段,第 5 节中记录的安全保证在此阶段尚不适用。

> ⁵ 这两个信任前顺序漏洞是 CVE-2025-59536(CVSS 8.7)和 CVE-2026-21852(CVSS 5.3)(Donenfeld and Vanunu, 2026),由 Check Point Research 发现。CVE-2025-54794 和 CVE-2025-54795(Beber, 2025)则是分别利用权限流水线其他位置的路径校验和命令解析缺陷。这四个漏洞都在披露后数周内得到修补。

这一模式揭示,权限流水线描绘的是安全检查的空间顺序,却没有捕捉时间维度:具体来说,就是在会话初始化期间,每种机制何时变得活跃。初始化序列(扩展加载,然后信任对话框,然后权限强制执行)造成了一个窗口,在这个窗口中,扩展性架构(第 6 节)先于安全架构(第 5 节)完全启用而运作。这一发现为"扩展性与简单性"的张力增添了一个安全维度,从而对其加以完善:扩展性造成攻击面,不仅通过组合复杂性,也通过初始化顺序。

**上下文效率 vs. 透明性。** 五层压缩流水线实现了有效的上下文管理,但压缩对用户在很大程度上是不可见的。当预算缩减用一个引用替换一个很长的工具输出、当上下文折叠用摘要取代消息(源码中描述为"对 REPL 完整历史的读时投影")、或当裁剪修剪较旧的历史时,用户没有简便的方法去检查丢失了什么。微压缩感知缓存的行为又增加了一层不透明性,因为压缩决策受到提示缓存的影响,而用户看不到这一点。关于基于摘要的压缩的外部研究记录了源码层面看不到的、除不透明性之外的两项成本:摘要步骤是一次阻塞式的推理停顿,而且是非确定性的,在相同输入上,保留的内容会随运行而波动(Cim et al., 2026)。

**简单性 vs. 扩展性。** 四种扩展机制使丰富的定制成为可能,但也产生组合性的相互作用。一个插件贡献一个修改工具输入的 PreToolUse hook。自动模式分类器读取被缓存的 CLAUDE.md 内容。路径限定规则在读取新目录时懒加载,可能在对话中途改变分类器的行为。权限处理器的四个分支在多个点与 hook 流水线相互作用。这些横切关注点造成了难以从任何单一配置文件预测的涌现行为。

### 12.4 实证预测与早期信号

本文记录的架构属性产生了关于代码质量结果的可检验预测,这些预测无法仅从源码推导出来。有限的上下文窗口(第 7 节)使智能体无法同时保持对整个代码库的觉知:五层压缩流水线保留了有用的信息,但在每一阶段都引入有损压缩。这使得从架构上可以预测:智能体生成的代码,相比具备完整代码库可见性所产生的代码,会表现出更高比例的模式重复和约定违反。子智能体隔离(第 8 节)使每个子智能体在自己的上下文窗口中运行,并拥有独立组装的工具池,从而加剧这一效应:并行的智能体可能独立地重新实现别处已经存在的解决方案。第 12.1 节的设计理念相信模型能做出良好的局部决策,但当模型缺乏全局上下文时,良好的局部决策可能产生糟糕的全局结果。

关于架构相似的工具的已发表实证工作,提供了与这些预测一致的数据。一项对 807 个仓库中 Cursor 采用情况的因果分析(He et al., 2025)发现,代码复杂度出现统计显著的增加,最初的速度飙升在第三个月消散至基线水平。复杂度上升与未来开发速度成比例的下降相关,表明短期收益可能被之后的维护成本所抵消。⁶ 一项针对 6,275 个仓库中 304,000 个 AI 撰写的提交的大规模审计(Liu et al., 2026)发现了可衡量的技术债,约四分之一由 AI 引入的问题持续存在于最新版本,而与安全相关的问题持续存在的比例则明显更高。尽管这些研究针对的是相邻系统,但架构上的相似性(有限上下文、工具调用循环、局部生成决策)使它们成为与此处分析的设计相关的比较点。一项在 Claude Code 本身上进行的受控最小对(minimal-pair)研究进一步明确了这些效应在何处可以被衡量:代码整洁度没有改变任务通过率,但更整洁的输入使 token 使用量降低了 7% 至 8%,文件的重复访问减少了 34%(Trivedi and Schmitt, 2026),这表明 harness 对上下文的处理,其最明显的体现是在运行成本和导航方面(成本与导航),而不是原始的成功率。

> ⁶ 复杂度 +40.7%(p < 0.001),第一个月速度飙升 +281%,第三个月回到基线水平。

Claude Code 的上下文管理流水线正是为缓解这些效应而专门设计的:分级压缩保留最近、最相关的上下文,感知缓存的压缩避免在压缩期间使提示缓存失效,读时投影在向模型呈现压缩视图的同时保留完整历史以供重建,而子智能体摘要隔离则防止探索性的噪声在父级上下文中累积。这些机制是否足以克服有限上下文的结构性局限,是一个可直接衡量的实证问题,本文的源码级分析无法解决。

### 12.5 局限性

除了附录中描述的方法论局限之外,还有若干分析上的约束。记忆化的上下文组装函数(getSystemContext() 和 getUserContext() 都在 context.ts 中使用 lodash 的 memoize)意味着 git 状态和 CLAUDE.md 内容是被缓存的,而不是每个回合都重新计算。对话期间的动态变化可能不会被立即反映出来,尽管压缩可以清除缓存,而懒加载的路径限定规则提供了部分的反向机制。

功能开关造成构建时的差异性。在 TRANSCRIPT_CLASSIFIER 为 false 的构建中,整个自动模式分类器会被消除。受功能开关控制的模块使用动态 require() 而不是静态 import(例如 query.ts 中的上下文折叠),因为由于 bun:bundle 的摇树(tree-shaking)约束,feature() 只在 if/三元条件中有效。不同的构建目标可能产生功能上不同的应用。

### 12.6 新兴方向

实现的若干方面与更广泛的设计问题相关。更长的上下文窗口会降低压缩压力,有可能简化分级流水线。多模态工具(截图、图表、UI 预览)会扩展工具面,并带来新的上下文挑战。对权限属性的形式化验证(例如,证明拒绝规则总是优先、沙箱化的命令无法逃逸隔离,或恢复的会话无法继承过时的权限)将提供更强的安全保证。

**架构解耦。** 这里分析的紧耦合本地架构,只是一个已在演化的谱系上的一个点。Anthropic 自己的 Managed Agents 工作(Martin et al., 2026)描述了对智能体各组件(会话、harness、沙箱)进行虚拟化,使得"每一个都成为对其他组件几乎不做假设的接口,并且每一个都可以独立地失效或被替换",并明确类比了操作系统如何把硬件虚拟化为进程和文件。《Harness 设计》一文(Rajasekaran, 2026)从另一个角度提出了类似观点,认为更好的模型改变的是有用 harness 组合的空间,而不是消除它。因此,本文记录的架构应当被理解为一个共同演化的系统的快照,而不是一个固定的最优点。

云智能体的报告在不依赖操作系统类比的情况下使这一点变得具体。Cursor 将智能体循环、机器状态和对话状态分离,并把虚拟机检查点、网络策略、密钥处理和凭据管理视为智能体产品的一部分(Ma, 2026)。LangChain 的 Managed Deep Agents 采取了类似的做法,把持久线程、检查点、流式输出、上下文、可观测性和人在回路(human-in-the-loop)工作流放置在托管运行时中(LangChain, 2026b)。Google 的 Antigravity 给用户提供计划、截图和录制内容等产物,以检查智能体的工作(Google, 2025)。因此,有价值的设计问题是运行时所有权:哪一层拥有循环、状态、沙箱、策略和恢复路径?

**记忆作为一等子系统。** Hu et al.(2025)的记忆综述认为,智能体记忆正在成为一个独立的认知基底,而不是上下文窗口管理的副作用,并把自动化记忆管理、强化学习驱动的记忆和可信记忆(隐私、可解释性和对幻觉的鲁棒性)确定为开放的前沿。Claude Code 如今暴露了事实层(CLAUDE.md、自动记忆)和工作层(对话窗口)。经验层(从过去会话中学到的、累积并自动整理的策略手册)是自然的下一步,而上下文工程文献(Zhang et al., 2025a)已经开始为这种累积提供机制。

**Context Hub 使边界变得可见。** LangSmith Context Hub 把 AGENTS.md 文件、skills、策略、示例和相关集合视为带版本、可审阅的产物,并带有用于跨环境部署的标签(LangChain, 2026a)。这与 Claude Code 的文件层级是不同的设计点,但它指出了同一个问题:上下文需要一个生命周期,而不只是一个 token 预算。

**可观测性与静默失败。** 行业调查表明,已部署智能体的主要失效模式不是崩溃,而是静默的错误。Bessemer 的 2026 年基础设施报告(Wade et al., 2026)估计"78% 的 AI 故障是不可见的",而 LangChain 有 1,340 名受访者的智能体工程现状调查(LangChain, 2026c)则指出,质量而非成本是生产使用的首要障碍,并发现可观测性(采用率近 89%)与离线评估(52.4%)之间存在很大差距。这里分析的架构为运营者提供了对工具调用、hooks 和会话转录的可见性。弥合评估差距很可能需要额外的脚手架(生成器—评估器分离、冲刺契约(sprint contracts)以及 Rajasekaran(2026)中讨论的那类事后检查),而不仅仅是模型改进。

OpenAI 的智能体改进循环使这一点具有了可操作性:追踪和反馈变成评测,所得到的证据成为交给 Codex 的、针对 harness 变更的交接(Pasfield, 2026)。在这个循环中,遥测之所以重要,是因为它会转化为可复用的测试或具体的变更请求。

**治理。** 随着智能体变得更加自主,更广泛的治理趋势将约束设计空间。《国际 AI 安全报告》(Bengio et al., 2026)警告说,"AI 智能体带来更高的风险,因为它们自主行动,使人类更难在故障造成伤害之前进行干预",而 MIT 的 AI Agent Index(Staufer et al., 2026)发现,在被收录的智能体系统中,只有 13.3% 发布了针对智能体的安全卡片(safety cards)。新兴的监管努力,包括欧盟《AI 法案》以及围绕 AI 生成代码不断演变的版权争论,可能会在日志记录、透明度、风险管理和人类监督方面施加外部约束,从而塑造编程智能体架构的演进。

**主动式架构。** 受功能开关控制的 KAIROS 系统说明了该架构如何可能演进到超越反应式工具使用。KAIROS 实现了一个带有基于 tick 的心跳的持久后台智能体:当没有待处理的用户消息时,系统会注入周期性的 <tick> 提示,由模型决定是行动还是休眠。该设计针对的是一项关于主动式 AI 助手的研究中记录的张力:任务完成度提高了 12% 至 18%,但在高频率下用户偏好下降(Chen et al., 2025)。KAIROS 试图通过终端焦点感知(用户不在时最大化自主行动,在场时增加协作)和通过 SleepTool 进行的经济节流来解决这一问题(每次唤醒都消耗一次 API 调用。提示缓存在五分钟不活动后过期,使休眠/唤醒成为一种显式的成本优化)。这种把主动性同时与用户在场情况和 token 经济学绑定的做法值得注意,尽管无法确认 KAIROS 在生产构建中是否处于活跃状态。

### 12.7 反复出现的设计选择

综合阅读六个子系统的分析,可以看到三个在原本相互独立的组件之间反复出现的贯穿性设计承诺。

**分级分层优于单体机制。** 安全、上下文管理和扩展性都使用分级的、由独立机制组成的堆栈,而不是单一的集成方案。权限架构分层了第 3.5 节列举的七个独立阶段:工具预过滤、默认拒绝的规则评估、权限模式约束、自动模式分类器、shell 沙箱、恢复时不还原会话权限,以及 hook 拦截。上下文管理分层了五个压缩阶段、懒加载的 CLAUDE.md 文件、延迟加载的工具模式,以及仅返回摘要的子智能体。扩展性分层了四种机制(MCP 服务器、插件、skills 和 hooks),上下文成本各不相同(第 6 节)。在每一种情形中,设计都以简单性和可调试性换取纵深防御,并接受层与层之间的相互作用会产生难以从任何单一配置预测的涌现行为。第 10 节中与 OpenClaw 和 Hermes Agent 的对比表明,分级分层在部署环境迥异的系统中反复出现,这说明这一分层模式反映的是共同的设计问题,而不是 Claude Code 特有的实现选择。

**偏向可审计性而非查询能力的仅追加设计。** 会话转录是仅追加的 JSONL 文件,带有读时链条修补。权限不会跨会话边界还原。上下文压缩对完整历史应用读时投影,而不是破坏性编辑。这一承诺之所以反复出现,是因为它保留了在不修改先前写入状态的情况下恢复、分叉和审计会话的能力。其代价是,更丰富的结构化查询(例如"显示所有会话中修改了文件 X 的工具调用")需要事后重建,而不是直接查找。

**在确定性 harness 内的模型判断。** 在所有子系统中,该架构都是在丰富的确定性 harness 之内信任模型的判断,而不是约束它的选择。估计的 1.6% 决策逻辑占比从数量上体现了这一点:harness 创造了让模型能够做出良好决策的条件(工具路由、权限强制执行、上下文组装、恢复逻辑)。层级化的权限在智能体边界之间保持安全不变量,assembleToolPool() 把内置工具和 MCP 工具合并成单一的统一接口,但模型对调用哪些工具以及按什么顺序调用保有完全的自由度。其权衡在于,当有限上下文妨碍全局觉知时,良好的局部决策可能产生糟糕的全局结果,正如第 12.4 节的实证预测所记录的那样。

## 13 未来方向

第 12 节把第 3 至 9 节记录的架构当作一个连贯的设计点来解读,并指出了这一设计点所隐含的张力、权衡和近期方向。本节超越架构本身,记录六个开放问题;这些问题在第 12.6 节中已被部分提及,并且不断增长的外部文献已将它们阐明到可以具体陈述的程度。这些问题涵盖本文的五价值框架(第 2.1 节)以及第 2.4 节引入的开发者长期能力问题。它们涉及:对决策权层级的治理约束(第 13.5 节)、安全一侧的可观测性—评估鸿沟(第 13.1 节)、可靠性一侧的跨会话持久化(第 13.2 节)、能力前沿的四种扩展(第 13.3 节)、作为可靠执行一个独立轴的时间跨度扩展(第 13.4 节),以及被重新表述为设计问题的开发者长期能力(第 13.6 节)。与第 12.6 节的框架一致,每个问题都以"是否/如何/哪个(whether / how / which)"的形式提出。当所引用的来源指明了具体的机制选择时,我们予以指明,否则就保持开放。

### 13.1 静默失败与可观测性—评估鸿沟

第 12.6 节中报告的可观测性—评估鸿沟,可能反映的是缺少一个工具层、harness 内部缺少评估接口,或者模型能力的天花板。那里的来源并未对此作出裁定。因此,该段所指出的"静默错误"失效模式应当如何被呈现,是 harness 的架构问题,而不是模型的能力问题。近期的实证工作在若干分辨率上刻画了这一鸿沟。Cemri et al.(2025)梳理了十四种失效模式,涵盖系统设计问题、智能体间的失准和任务验证。Pathak et al.(2025)构建了一个专门用于追踪异常检测的智能体轨迹基准。Yao et al.(2024)通过 pass^k 指标(k 次独立试验全部成功的概率)揭示了一致性鸿沟。Kapoor et al.(2024)认为,当前的智能体基准缺乏留出集(holdout)和成本控制,限制了可观测性实际上能够诊断的内容。

针对第 4 和第 5 节中分析的权限流水线和工具编排层,仍有两个架构问题悬而未决。第一,本文引用 Rajasekaran(2026)的脚手架(生成器—评估器分离、冲刺契约、事后检查,建立在 Madaan et al.(2023)的自我精炼(self-refine)模式之上)应当属于 harness 内部(例如,作为第 6 节所记录的 27 个之外的额外 hook 事件),还是作为一个单独的评估层位于其外部,所引用的来源并未解决。第二,第 6 节现有的 hook 流水线能否在其当前的上下文成本范围内承载这类脚手架,是另一个悬而未决的问题。关于弥合这一鸿沟"很可能需要额外的脚手架……而不仅仅是模型改进"(第 12.6 节)的观察,把待完成的工作定位在 harness 层。

### 13.2 持久化:记忆与纵向的同事关系

智能体状态以及人—智能体的工作关系是否应当跨会话持久,以及以何种形式持久,本文目前在两个不同的层面处理。第 7 节记录了四级 CLAUDE.md 层级和自动记忆。第 9 节记录了大体仅追加的 JSONL 转录,其会话范围的权限在恢复时不会被还原,显式的清理重写除外。介于这两层之间应当有什么,是一个开放的设计问题:既不是静态指令,也不是单个会话转录的持久状态。第 12.6 节已经引用的 Hu et al.(2025)和 Zhang et al.(2025a)推动了一个累积层的设想。Packer et al.(2023)把 LLM 重新框定为带分页内存的操作系统。Chhikara et al.(2025)构建了一个面向生产的、能够在重启后留存的记忆存储,而 Xu et al.(2025)提出了一个研究性的智能体记忆设计。Wang et al.(2024c)捕捉可复用的过程性轨迹。Shinn et al.(2023)通过跨次尝试的言语强化来累积自我反思轨迹。Zhang et al.(2025b)和 Huang et al.(2026)的综述梳理了候选机制。

**MemGym** 使记忆问题更加具体。它评估的是跨工具使用对话、深度研究、编程和计算机使用的动态记忆形成,而不仅仅是聊天中个人事实的保留(Xu et al., 2026)。这使问题从"笔记应当存放在哪里?"转变为"记住的哪些状态有助于智能体保持正确工作?"

同样的持久化问题在人这一侧也会重现。第 12.6 节已引用了来自 Huang et al.(2025)和 McCain et al.(2026)的纵向自主性证据。Dell'Acqua et al.(2025)对 776 名宝洁公司专业人员的现场实验,连同对 Copilot 推广(Stray et al., 2025)和 AI 团队协作轨迹(Xiao et al., 2025)的纵向和组织研究,报告了随着协作累积,人—AI 工作动态所发生的转变。Wang et al.(2023)展示了一个跨任务累积技能库的具身智能体。Mollick(2024)把人—AI 工作关系框定为"共同智能(co-intelligence)"。一个单一的基底能否既承载用户的个人指令层级,又承载共享的组织上下文,同时保留第 7 节所记录的 CLAUDE.md 基于文件的透明性,是一个开放的架构问题。会话范围的权限如何与这样的基底相互作用,而不重新引入第 9 节作为一项有意的安全选择而关闭的"恢复时还原"问题,则是另一个开放问题。第 10 和 10.2 节中记录的 OpenClaw 记忆子系统(做梦、每日笔记、混合检索)和 Hermes Agent 带全文搜索的 WAL 模式 SQLite 会话存储,提供了两个具体的参考点,说明持久基底如何可以介于静态指令层级与单会话转录之间。

### 13.3 Harness 边界的演进:智能体在何处、何时、对什么、与谁一起行动

第 12.6 节引用了 Rajasekaran(2026)的论点:更好的模型改变的是有用 harness 组合的空间,而不是消除它。这种变化最显著地体现在 harness 在何处运行、何时行动、对什么行动,还是与谁协调,第 3 至 9 节的源码级分析并未解决。这四者各有活跃的研究文献,本文只是顺带提及。

**何处(Where)。** Martin et al.(2026)的 Managed Agents 设计把会话、harness 和沙箱虚拟化为可独立替换的接口。这扩展了 Packer et al.(2023)应用于上下文窗口管理、并由 Karpathy(2023)更广泛地推广的虚拟内存类比。Khattab et al.(2023)则把 harness 本身视为一个编译目标。

**何时(When)。** 第 12.6 节已经把 KAIROS 作为一个受功能开关控制的例证引入,其动机是 Chen et al.(2025)报告的 +12% 至 +18% 的任务通过率提升,以及仅限于高频的"持续建议(Persistent Suggest)"变体的显著偏好惩罚(47% 对 80% 至 90%)。Liu et al.(2025)、Pu et al.(2025)和 Lee et al.(2025)把主动性的设计空间扩展到编程和环境式界面场景。Pasternak et al.(2025)和 Sun et al.(2025)引入了旨在提升主动性的基准和训练方案,Deng et al.(2025)则综述了更广泛的文献。

**对什么(What)。** 视觉—语言—动作(VLA)的工作把 harness 扩展到文本形式的工具返回之外。Brohan et al.(2023)和 Black et al.(2024)训练执行物理动作的 VLA 策略,Ahn et al.(2022)把计划建立在机器人的可供性(affordance)之上。Figure AI(2025)和 Bjorck et al.(2025)等工业系统把类似的思想推进到人形机器人的控制。这些系统面临表 1 中的"按可逆性加权的风险"原则,其成本不对称性是该原则指出但没有对非文本动作进行量化的。

**与谁(With whom)。** 角色分化的多智能体系统(Hong et al.(2023)、Li et al.(2023)、Chen et al.(2023)、Qian et al.(2024))组合了具有不同职责的智能体。多智能体辩论(Du et al., 2024;Liang et al., 2024)和图结构的工作流(Zhuge et al., 2024)探索了第 8 节父/子智能体模式之外的替代方案。Guo et al.(2024)综述了这一领域。

单一的 harness 架构能否涵盖这四种扩展,还是 Rajasekaran(2026)所描述的"harness 组合"将碎片化为专门化的堆栈,是一个开放的设计问题。"何时"这一扩展直接延续了表 6 中的"能力对适应性"张力。"与谁"这一扩展部分地对应于"能力对可靠性",但提出了表 6 本身未涵盖的跨智能体一致性问题。"何处"和"对什么"这两项扩展提出了本文当前子系统边界未涵盖的进一步问题:当 harness 组件成为托管服务时,会附带哪些治理义务(第 13.5 节),以及按可逆性加权的风险(表 1)如何扩展到物理而非文本的影响。这些扩展如何跨轴组合,而不是在单个轴之内组合,这不是本文的单子系统分析所能解决的。

### 13.4 时间跨度扩展:从会话到科学计划

第 2.1 节把可靠执行定义为涵盖"单回合正确性与长时程的可靠性"。当自主工作延伸到单个会话之外时,第 3、4 以及 7 至 9 节所记录的架构如何继续支持长时程的可靠性,是一个开放问题。其主要单位是回合、会话和子智能体。不断增长的文献针对这一领域。Lu et al.(2024)提出了一条端到端的自主研究流水线,可生成论文草稿。Beel et al.(2025)对该流水线提供了独立的 SIGIR Forum 评估,刻画了"自主研究"目前能交付什么以及在哪些方面不足。Gottweis et al.(2025)开发了一个多智能体假设生成系统,运行时间以天而不是回合计,Novikov et al.(2025)则在以往需要人类专家数周的时间尺度上追求算法发现。Kwa et al. 的 METR 研究测量了前沿智能体以固定可靠度成功完成的任务时长,为这一扩展问题提供了实证框架。

"量化目标持久性(Quantitative Goal Persistence)"基准指出了一种更窄的失效模式:智能体可以做出合理的局部工具调用,却仍然在验证器确认足够多的有效工作单元之前就停止(Cai et al., 2026)。对于长时程的编程智能体,进展需要一个外部的"完成"概念,而不仅仅是一条流畅的最终消息。

对照本文的分析,长时程部署检验的是:当会话组合成多会话计划时,第 7 节的上下文管理流水线、第 8 节的"最后一条助手文本返回"策略,以及第 9 节的仅追加持久化是否仍然足够。第 12.4 节已经把这一点表述为"一个可直接衡量的实证问题",源码级分析无法解决。时间跨度扩展则是在以周计的尺度上重述了这个问题:仅靠 harness 层是否能弥合差距,是否需要跨会话的记忆基底(第 13.2 节),还是长时程工作需要超出会话、子智能体和记忆之外的协调原语,这不是本文以会话为范围的分析所能确定的。

**(A 级证据)** 在此处分析的 v2.1.88 快照之后的一项进展,使这个问题变得具体。Claude Code v2.1.154 引入了动态工作流(dynamic workflows):由模型编写一段 JavaScript 编排脚本,由后台运行时执行,扇出到许多子智能体(每次运行上限为一千个),而中间结果存放在脚本变量中,位于模型的上下文窗口之外,而不是经过它(Anthropic, 2026i)。该功能与 Claude Opus 4.8(Anthropic, 2026h)同时发布,这恰恰是一个超出此处分析的会话、子智能体和记忆单位之外的协调原语:它把编排逻辑本身从对话中搬了出来,把"将上下文视为稀缺资源"和"隔离的子智能体边界"这两条原则(表 1)从单个子智能体扩展到了编排层。"编排即代码(orchestration-as-code)"是否会成为主导的长时程原语,以及它的 token 成本和减少的运行中人类监督如何与其可靠性收益相权衡,是此处以会话为范围的分析无法解决的开放问题。

### 13.5 大规模下的治理与监督

新兴的 AI 监管为实现第 2.1 节所记录的"Anthropic、运营方、用户"决策权层级的架构增加了一项外部约束。在这一外部约束下,编程智能体架构应当暴露哪些日志、透明度和人类监督的功能,仍然是一个开放的设计问题。欧盟委员会的 GPAI 行为准则(European Commission, 2025a)和实施指南(European Commission, 2025b)说明了通用 AI 治理正在朝着对文档、风险管理、透明度和监督提出更明确期望的方向发展。第 12.6 节已引用的 MIT AI Agent Index(Staufer et al., 2026)和《国际 AI 安全报告》(Bengio et al., 2026),推动了这一约束在披露和监督方面的一侧。Bartz v. Anthropic 的裁决(bar, 2025)增加了一项针对训练数据来源的输入侧约束,这与新兴案件另行处理的、关于 AI 生成代码的输出侧版权问题是不同的。经合组织(OECD)关于 AI 治理框架的报告(OECD, 2025)以及 Nannini et al.(2026)对智能体提供者合规义务的早期分析,勾勒出了面向监管者的接口可能是什么样子,但没有规定具体细节。

**(A 级证据)** 监管不仅可以作用于一个架构必须披露什么,也可以作用于模型的可用性。2026 年 6 月,一项美国出口管制令禁止外国公民使用 Anthropic 的 Fable 5 和 Mythos 5 模型,并且在发布后的数天内,Anthropic 对全球所有用户禁用了这两个模型(Anthropic, 2026d)。这类政府政策可以直接决定这样一个模型是否还能继续部署。

智能体安全基准也把安全对象从文本转向了环境状态。"Boiling the Frog"评估多轮工作区编辑在渐进式攻击下是否会变得不安全(Bisconti et al., 2026)。这对编程智能体很重要,因为有风险的对象可能是被修改过的代码仓库,而不是最终的回答文本。

对照第 5 节分析的权限流水线,在这一约束之下,当前架构的两个属性是开放的。第一,本文所记录的默认拒绝评估,可以通过会话转录(第 9 节)进行内部审计,但尚不能以 GPAI 行为准则(European Commission, 2025a)等新兴框架所设想的形式进行外部审计。第二,本文将"价值观优先于规则"原则与确定性护栏配对,而该原则是否允许合规审查可能要求的那种显式规则表述,是另一个开放问题。这两个属性都位于 harness 而非模型之内,而这正是未来架构可能需要暴露新接口的地方。

### 13.6 开发者的长期能力

第 2.4 节把开发者长期能力作为一个贯穿性问题引入,而非一项同等地位的设计价值。第 12.2 和 12.4 节用外部证据扩展了这个问题,包括感知与实测生产力的差异、理解力丧失、复杂度累积、技术债的持续存在、神经连接减弱的持续存在,以及早期职业招聘的下降。从业者也这么说:在反思自己转向由智能体驱动的编程时,Karpathy(2026)警告说,"你可以外包你的思考,但你无法外包你的理解。"第 14 节随后转向:"未来的系统可以把这种可持续性缺口视为一等的设计问题,而不是下游的评估指标。"这种转向是否可能,以及一等对待需要什么样的架构机制,是本节记录的最后一个开放问题。

这也与过程监督相关联。人—LLM 协同规划的工作认为,用户需要的是过程级控制,而不仅仅是结果级审阅,并按模式、范围和编辑层级来组织引导(He et al., 2026)。对于编程智能体,类似的问题是:在工作仍在展开的过程中,用户可以检查和更改什么。

有两个子问题把测量缺口与设计缺口区分开来。第一,推动这个问题的实证主张在会话粒度上是否可测量。现有的引用工作的尺度是从会话到数月(Becker et al.(2025)的 16 名开发者 RCT、Shen and Tamkin(2026)的理解力测试比较、Kosmyna et al.(2025)的 EEG 研究、He et al.(2025)的 807 仓库因果分析、Liu et al.(2026)的 30.4 万提交审计、Rak(2025)的招聘序列),但第 3、4 以及 7 节记录的 harness 并未暴露针对理解力或约定漂移的逐会话信号。关于程序员交互模式的相关工作(Barke et al., 2023)和 AI 引起的代码安全退化(Perry et al., 2023)勾勒了会话粒度的测量,Aiersilan(2026)则提出了会话级认知卸载探测的协议。第二,一旦这些测量存在,架构能否对其作出响应(应用于人类循环的生成器—评估器分离(Rajasekaran, 2026)的类比、保护理解力的界面,或尚未命名的机制),是第 14 节提出的设计缺口问题。本文对适合哪一类机制不持立场。本文也没有确定,此处所记录的 harness 是否是采取这种行动的合适位置,而不是 IDE、组织或人类的开发循环。第 11 节所综述的相关工作和第 14 节的可持续性转向,标出了本文把这个问题留在何处。

## 14 结论

本文表明,生产级编程智能体可以被理解为对一组反复出现的设计问题的回答:推理相对于 harness 位于何处,执行、安全、扩展性、上下文、委派和持久化如何组织,以及这些选择编码了哪些权衡。Claude Code 在该空间中占据一个清晰的设计点。它赋予模型广泛的局部自主权,同时用一个稠密的确定性 harness 围绕它,负责权限控制、工具路由、上下文压缩、扩展性和会话恢复。通过第 2 节中识别的五项价值和十三条设计原则来审视,这些选择是连贯的,而不是临时拼凑的:该系统始终如一地优先考虑人类决策权、安全、可靠执行、能力放大和情境适应性。

与 OpenClaw 和 Hermes Agent 的比较表明,同样的设计问题在不同的智能体系统中反复出现,但产生不同的答案。Claude Code 在 CLI harness 之内投入于逐操作的安全分类和分级的上下文压缩,OpenClaw 在多渠道网关之内投入于边界级的访问控制和结构化的长期记忆,而 Hermes Agent 则从单一进程出发,在众多界面上呈现逐操作批准,并带有可插拔的记忆和模型后端。这三个系统通过 ACP 在多个位置上组合:OpenClaw 可以通过 ACP 把 Claude Code 作为外部 harness 托管,而 Hermes Agent 位于主机/客户端划分的两侧。因此,对智能体构建者而言,最具影响的开放问题不是如何增加更多自主性,而是如何随时间保持人类的能力。

综合而言,第 2.4 节引入的长期能力问题、第 12 节的分析,以及第 13 节所综述的开放问题表明:该架构为明确保护人类长期的理解力、代码库一致性或开发者人才梯队所提供的机制是有限的。未来的系统可以把这种可持续性缺口视为一等的设计问题,而不是下游的评估指标。

### 证据基础与方法论

本附录记录了本研究的证据来源、分析流程与局限。

**证据基础与证据等级**

本文的论断建立在三个证据等级之上:

- **A 级(产品文档记载):** 取自 Anthropic 官方文档和工程出版物的论断。它们确立了产品意图,但可能并不反映内部实现。
- **B 级(代码验证):** 引用所提取的 TypeScript 代码库(v2.1.88,取自公开可得的 npm 包提取物)中具体文件和函数的论断。这是最强的证据等级。
- **C 级(重构):** 源自社区分析、OpenClaw 或 Hermes Agent 的结构对比,或从代码模式推断的论断。这些论断以带有保留的措辞来陈述。

源码语料库包含约 1,884 个文件,共计约 51.2 万行 TypeScript。OpenClaw 和 Hermes Agent 被用作比较参照点,而不是真值标准。

**设计空间分析流程**

设计问题是通过考察每个子系统中存在其他生产级智能体采用备选设计的、反复出现的选择点而识别出来的。Claude Code 对每个问题的回答,都通过具体的源文件和函数实现进行追溯(B 级证据)。五价值框架(人类决策权、安全与隐私、可靠执行、能力放大和情境适应性)是从官方文档和创造者的陈述中识别出来的(A 级),然后通过十三条设计原则追溯到架构决策。长期能力保持被单独视为一个贯穿性问题,而不是一项设计价值,因为它在架构中以及在 Anthropic 所陈述的价值中,并未被突出地体现为设计驱动因素(第 2.4 节)。Token 经济学作为一个贯穿性约束,同时约束全部五项价值,揭示了在共享的资源压力下,各个子系统的选择如何相互作用。

**局限性**

- **静态快照。** 分析反映的是一个版本(v2.1.88)。功能开关(例如 TRANSCRIPT_CLASSIFIER、CONTEXT_COLLAPSE)造成构建时的差异性。不同的构建目标可能产生功能上不同的应用。
- **逆向工程认识论。** 源码揭示的是已实现的结构、控制流、依赖关系和功能开关。它无法确认设计意图、生产环境中启用的开关、运行时的普及程度,或尚未发布的行为。
- **单系统分析。** 研究发现描述的是 Claude Code 的设计空间,而不是编程智能体的整个设计空间。推广是有限度的。
- **对比系统的快照。** 对 OpenClaw 和 Hermes Agent 的分析各自反映的是特定的开发状态,可能不代表它们当前的能力。
