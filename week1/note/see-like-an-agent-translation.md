# 像智能体一样看问题:设计 Claude Code 的工具(译文整理)

## 开篇

构建智能体框架(agent harness)时,最难的部分之一就是设计它的行动空间。

Claude 通过工具调用(Tool Calling)来行动,而在 Claude API 中,构建工具的方式有很多种,比如 bash、skills,以及最近推出的代码执行(想了解 Claude API 上的程序化工具调用,可以阅读 [@RLanceMartin 的新文章](https://x.com/RLanceMartin/status/2027450018513490419))。

面对这么多选项,你该如何设计智能体的工具?只需要一个工具,比如代码执行或 bash 吗?还是为智能体可能遇到的每个用例各准备一个工具,总共 50 个?

为了设身处地站在模型的角度思考,我喜欢想象自己拿到了一道很难的数学题。你会想要什么工具来解决它?这取决于你自己的能力!

纸是最基本的,但你会被手算所限制。计算器更好,但你得知道如何操作那些更高级的功能。最快、最强大的选择是电脑,但前提是你得会用它来编写和运行代码。

这是一个设计智能体时很有用的思考框架:你应该给它提供与其自身能力相匹配的工具。但你怎么知道它的能力是什么呢?靠观察、阅读它的输出、不断实验。你要学会"像智能体一样看问题"(see like an agent)。

下面是我们在开发 Claude Code 的过程中,通过观察 Claude 总结出的一些经验。

## 改进信息获取与 AskUserQuestion 工具

在构建 AskUserQuestion 工具时,我们的目标是提升 Claude 提问的能力(通常称为 elicitation,即信息获取)。

Claude 完全可以直接用纯文本提问,但我们发现,回答这些问题会花费不必要的时间。我们该如何降低这种摩擦,并提高用户与 Claude 之间的沟通带宽?

**方案一:给 ExitPlanTool 增加参数。** 我们尝试的第一个方案,是给 ExitPlanTool 增加一个参数,让它在返回计划的同时附带一个问题数组。这是最容易实现的做法,但它让 Claude 感到困惑,因为我们同时要求它给出一份计划,以及一组关于这份计划的问题。如果用户的回答与计划中的内容相冲突怎么办?Claude 是否需要调用两次 ExitPlanTool?我们需要换一种思路。

**方案二:修改输出格式。** 接下来,我们尝试修改 Claude 的输出指令,让它按照一种略作调整的 markdown 格式来提问。例如,我们可以要求它输出一个要点式的问题列表,并把备选项放在括号里。然后我们再解析这些内容,将问题渲染成给用户看的界面。

这是我们能做出的最通用的改动,Claude 似乎也能比较好地输出这种格式,但无法保证每次都如此。Claude 有时会多附加几句话,有时会漏掉某些选项,有时甚至会采用完全不同的格式。

**方案三:独立的工具。** 最后,我们决定创建一个 Claude 可以随时调用的工具,不过在计划模式(plan mode)下,我们会特别提示它去使用这个工具。工具被触发时,我们会弹出一个模态框来展示问题,并阻塞智能体的循环,直到用户作出回答。

这个工具让我们可以引导 Claude 给出结构化的输出,也帮助我们确保 Claude 会给用户提供多个选项。它还让用户可以灵活组合这项功能,例如在 Agent SDK 中调用它,或是在 skills 中引用它。

最重要的是,Claude 似乎很喜欢调用这个工具,而且我们发现它的输出效果很好。再精心设计的工具,如果 Claude 不理解该如何调用,也是没用的。

这是 Claude Code 中信息获取的最终形态吗?我们也不确定。正如你将在下一个例子中看到的,对一个模型有效的方案,未必最适合另一个模型。

## 随能力更新:Tasks 与 Todos

当我们最初发布 Claude Code 时,我们意识到模型需要一份 Todo 列表来保持工作不跑偏。Todos 可以在开始时写好,并在模型完成工作的过程中逐项勾掉。为此,我们给了 Claude 一个 TodoWrite 工具,用来写入或更新 Todos,并将它们展示给用户。

但即便如此,我们仍然经常看到 Claude 忘记自己该做什么。为了应对这个问题,我们每隔 5 轮就插入一条系统提醒(system reminder),提醒 Claude 它的目标。

然而随着模型不断进步,它们不仅不再需要被提醒 Todo 列表,甚至会觉得它是一种限制。不断收到 Todo 列表的提醒,会让 Claude 觉得自己必须严格遵守这份列表,而不是去修改它。我们还看到 Opus 4.5 在使用子智能体(subagents)方面变得强了很多,但子智能体之间该如何围绕一份共享的 Todo 列表进行协作呢?

基于这些观察,我们用 Task 工具取代了 TodoWrite([在这里了解更多关于 Tasks 的内容](https://x.com/trq212/status/2014480496013803643))。Todos 的作用是让模型保持在正轨上,而 Tasks 更多是帮助智能体之间相互沟通。Tasks 可以包含依赖关系,可以在子智能体之间共享进展更新,模型也可以修改和删除它们。

随着模型能力的提升,模型过去需要的工具,现在可能反而会限制它们。因此,持续重新审视"需要哪些工具"这一先前假设,非常重要。这也是为什么只支持少数几个能力特征相近的模型是很有帮助的。

## 设计搜索工具:让 Claude 自己构建上下文

对 Claude 来说,有一类特别重要的工具,就是帮助它自己构建上下文的搜索工具。

Claude Code 刚推出时,我们使用 RAG 向量数据库来为 Claude 查找上下文。RAG 虽然强大且快速,但它需要建立索引和配置,而且在各种不同的环境中比较脆弱。更重要的是,上下文是被"喂"给 Claude 的,而不是由 Claude 自己去找的。

但既然 Claude 可以搜索网页,为什么不能搜索你的代码库呢?通过给 Claude 一个 Grep 工具,我们让它可以自己搜索文件并构建上下文。

随着 Claude 变得越来越聪明,我们看到了这样一个规律:只要给它合适的工具,它就越来越擅长构建自己的上下文。

在推出 Agent Skills 时,我们将"渐进式披露"(progressive disclosure)这一理念正式确立下来,让智能体可以通过探索,逐步发现相关的上下文。Claude 可以读取 skill 文件,而这些文件又可以引用其他文件,模型可以递归地继续读取。事实上,skills 的一个常见用途,就是为 Claude 增加更多搜索能力,比如告诉它如何使用某个 API 或查询某个数据库。

在一年的时间里,Claude 从基本无法自己构建上下文,发展到能够跨越多层文件进行嵌套搜索,找到它所需要的确切上下文。

如今,渐进式披露已经成为我们常用的技术,可以在不增加新工具的情况下为智能体添加新功能。

## 渐进式披露:Claude Code Guide 智能体

Claude Code 目前有大约 20 个工具,我们也在不断自问是否真的需要全部这些工具。新增一个工具的门槛很高,因为这会让模型多出一个需要考虑的选项。

举个例子,我们注意到 Claude 对如何使用 Claude Code 了解得不够。如果你问它怎么添加 MCP,或者某个斜杠命令是做什么的,它答不上来。

我们本可以把这些信息全部放进系统提示词,但考虑到用户很少问这类问题,这样做会增加上下文腐化(context rot),并干扰 Claude Code 的主要任务:写代码。

于是,我们尝试了一种渐进式披露的做法:给 Claude 一个指向其文档的链接,让它按需加载并搜索更多信息。这个办法可行,但我们发现,Claude 为了找到正确答案,会把大量结果载入上下文,而实际上你只需要答案本身。

所以我们构建了 Claude Code Guide 子智能体,当用户询问 Claude 自身的问题时,Claude 会被提示去调用它。这个子智能体带有详尽的指令,说明如何高效地搜索文档,以及应该返回什么内容。

这种做法并不完美,当你问 Claude 如何配置它自己时,它仍然可能会感到困惑,但已经比以前好多了!我们成功地在不增加工具的情况下,扩展了 Claude 的行动空间。

## 艺术,而非科学

如果你希望得到一套关于如何构建工具的严格规则,很遗憾,这篇指南不是。为模型设计工具,既是科学,也是艺术。它在很大程度上取决于你使用的模型、智能体的目标,以及它所处的环境。

多做实验,阅读它的输出,尝试新事物。像智能体一样看问题(See like an agent)。

# 附:我的提问与解答整理

## 问题 1:"Claude 忘记自己该做什么"的问题,是靠模型能力提升解决的,而不是 harness,对吗?

**基本对,但更细一点:**

- 问题本身消失,根本上靠的是**模型变强**:模型自己能记住并调整目标了。
- harness 的角色是**先补偿弱点,再随模型进步撤掉补偿、转向新需求**。早期的 TodoWrite 加每 5 轮系统提醒,是对当时模型弱点的补偿;后来换成 Task 工具,目的变成支持子智能体协作(依赖关系、共享进展)。
- 这正是作者想表达的:harness 里的机制是针对特定能力水平设计的,模型变了就要重新审视,否则昨天的"拐杖"会变成今天的"枷锁"。

## 问题 2:最后 Claude 是如何解决 "action space" 问题的?

文章没有给出一劳永逸的解法,而是一套思路:**不靠不断加工具,而是让 Claude 用少量工具自己扩展能力。**

1. **工具要匹配模型的能力**:通过观察输出、不断实验来判断。
2. **新增工具门槛很高**:Claude Code 只有约 20 个工具,每多一个,模型就多一个要权衡的选项。
3. **用渐进式披露,在不加工具的情况下扩展能力**:Grep 让它自己搜代码库,取代 RAG 喂上下文;Skills 让它读文件并递归发现信息;Claude Code Guide 子智能体处理"问自身用法"这类低频需求,只把答案返回。
4. **工具随模型进步而调整**:如 TodoWrite 换成 Task 工具。
5. **工具设计要让模型"好调用"**:如 AskUserQuestion 用结构化的工具调用,而不是特殊格式的文本。

**一句话总结:** 保持工具集精简,把新能力放进 skills、子智能体这类可按需展开的机制里,并持续根据模型能力变化调整。

## 问题 3:什么是 "action space"?

**Action space(行动空间)** 指智能体在任何时刻**可以采取的所有动作的集合**。对 Claude 来说,它做事的唯一方式是调用工具,所以行动空间基本就是**它能调用的工具,以及每个工具能做的事**(bash 能执行命令,Grep 能搜索代码库,AskUserQuestion 能向用户提问,Task 能创建任务并与子智能体协作)。

这个术语来自强化学习:智能体每一步都要从"动作集合"中选一个动作。

**为什么设计行动空间很难?**

- **太小**:模型能力被限制,很多事做不了(只有纸和笔)。
- **太大**:选项太多,模型容易困惑或选错(50 个工具)。
- **不匹配模型能力**:太复杂模型不会用,太简单又束缚它。

所以"在不增加工具的情况下扩展行动空间",意思是:**让 Claude 能做的事变多了,但它要面对的工具选项没有变多。**
