RPPIT实践guidelines

在实际工作中使用 RePPIT 框架的实用方法RePPIT（Research → Propose → Plan → Implement → Test）最适合处理中大型、陌生或生产级的功能开发，而不是简单的小改动。下面是一套可直接落地的工作流：1. 什么时候用？需要改动多个文件、涉及现有架构的功能
接手不熟悉的代码库
要求上线到生产环境、质量要求高
一次性 vibe coding 很容易出问题的场景

简单 bug 修复或加个小按钮，直接用就行，没必要走完整流程。2. 实际操作步骤（推荐用 Claude Code / Cursor / Windsurf 等）Step 1: Research（研究代码库）目标：让 Agent 先全面理解现状，而不是急着写代码。提示词示例：text

请只做研究，不要提出任何解决方案或改进建议。

任务：为 [功能描述] 做代码库调研。
请输出一份结构化的研究报告，包含：
- 相关的文件和目录结构
- 核心组件/模块的职责
- 数据流和调用关系
- 现有相关功能的实现方式
- 测试覆盖情况
- 任何重要的约束或约定

只描述“现在是什么”，不要说“应该怎么改”。

产出：一份 Research Document（研究文档）。保存好，后面步骤都要用。Step 2: Propose（提出方案）目标：生成 2-3 个不同思路的方案，供你选择。提示词示例：text

基于以下研究报告：
[粘贴 Research Document]

现在要新增功能：[功能描述]

请提出 2-3 个明显不同的技术方案。每个方案包含：
- 核心思路
- 优点和缺点
- 影响范围（大概会改哪些模块）
- 风险点

不要实现，只提方案。

你的动作：阅读后选择一个方案（或混合），明确告诉 Agent 选哪个。Step 3: Plan（制定详细计划）目标：把选定方案变成可执行的详细设计文档。提示词示例：text

我们选择方案 X。

请基于研究报告和选定方案，输出一份详细的实现计划（Design Doc），包含：
- 功能需求和验收标准
- 具体要修改/新增的文件列表
- 每个文件的改动要点
- 数据模型变化（如果有）
- 关键点
- 测试策略
- 明确不在范围内的内容

产出：一份清晰的 Plan 文档。这一步很关键，能大幅减少后续返工。Step 4: Implement（实现）目标：严格按照 Plan 执行。提示词示例：text

请严格按照以下实现计划进行编码：
[粘贴 Plan 文档]

要求：
- 一次只改相关文件
- 每完成一个逻辑单元就停下来让我确认
- 不要擅自扩大范围

可以分阶段执行（比如先改后端，再改前端）。Step 5: Test（测试）目标：验证正确性，并补充测试。提示词示例：text

功能已实现，请：
1. 编写必要的单元测试 / 集成测试
2. 运行现有测试套件，确保没有破坏
3. 手动验证关键路径
4. 列出我需要手动检查的点
